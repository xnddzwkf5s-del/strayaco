OpenClaw Dashboard Offline After Update? Here's the Fix

OpenClaw macOS LaunchAgent Automation DevOps

Every time you update OpenClaw, the dashboard goes offline. You SSH in, fiddle with configs, restart the service, and 10 minutes later it's back. Next update — same thing. Here's why it happens and how to fix it permanently.

See also: If your dashboard comes back but model switching fails with 401 errors, you might have a related but separate problem: API key corruption from unresolved $(security ...) shell injection. Read OpenClaw API Key Corruption: Anatomy of a Silent 401 for the permanent fix.
TL;DR: The LaunchAgent plist gets silently replaced during updates, wiping your custom port and environment variables. The fix is a pre-update backup script and a post-update restore script. Total fix time: 10 seconds instead of 10 minutes.

Root Cause: The LaunchAgent Plist Problem

OpenClaw on macOS runs as a LaunchAgent — a background service managed by launchd. Its configuration lives in a single file:

~/Library/LaunchAgents/ai.openclaw.gateway.plist

This plist contains everything the service needs to start: the Node.js path, the gateway command, the port number, environment variables (including API keys), and log paths.

When you run openclaw update (or brew upgrade openclaw), the update process calls openclaw gateway install --force under the hood. That command writes a fresh plist from a template — and the template doesn't know about your custom port, your custom PATH, or your API keys.

The result: the service tries to start with a vanilla config, fails silently, and your dashboard is dead.

What Gets Wiped

SettingBefore UpdateAfter Update
Port18789 (custom)18789 or default (may change)
PATHFull Homebrew + user pathsMinimal (or missing)
API keysANTHROPIC, DEEPSEEK, etc.Gone
Auth tokenYour gateway tokenGone
Log pathsCustom locationsDefault locations

There are actually three separate failure modes:

  1. Plist overwrite: The plist is replaced with a vanilla one. Missing port, missing env vars, service fails to start.
  2. API key desync: Even if the plist survives, models.json can fall out of sync with your real config. The gateway loads, but model switching fails with "assistant turn failed before producing content" because models.json still has placeholder keys like YOUR_ANTHROPIC_API_KEY.
  3. Env file corruption: ~/.openclaw/.env contains unresolved $(security ...) shell commands. Every install --force reads this file and regenerates the poisoned service env. Model calls return 401 with Your api key: **** -w) is invalid. See the API Key Corruption post for the permanent fix.

The Fix: Automated Backup and Restore

Two scripts. One runs before the update, one runs after. Together they eliminate the problem.

Pre-Update Backup Script

Save this as ~/.openclaw/scripts/pre-update-backup.sh and make it executable with chmod +x:

#!/bin/bash
# Run BEFORE updating OpenClaw. Saves everything needed to recover.
set -e

BACKUP_DIR="$HOME/.openclaw/backups/$(date +%Y%m%d_%H%M%S)"
mkdir -p "$BACKUP_DIR"

echo "=== OpenClaw Pre-Update Backup ==="
echo "Backup dir: $BACKUP_DIR"

# 1. Plist (the most fragile piece)
cp ~/Library/LaunchAgents/ai.openclaw.gateway.plist "$BACKUP_DIR/"
echo "✓ Plist saved"

# 2. Config
cp ~/.openclaw/openclaw.json "$BACKUP_DIR/"
echo "✓ Config saved"

# 2b. State-dir .env (source of truth for API keys — prevents corruption)
cp ~/.openclaw/.env "$BACKUP_DIR/.env" 2>/dev/null \
  && echo "✓ .env saved" \
  || echo "- .env file not found (ok)"

# 3. Models config (gets out of sync sometimes)
cp ~/.openclaw/agents/main/agent/models.json \
   "$BACKUP_DIR/models.json" 2>/dev/null \
   && echo "✓ Models saved" \
   || echo "- Models file not found (ok)"

# 4. Current version
openclaw --version > "$BACKUP_DIR/version.txt" 2>/dev/null
echo "✓ Version: $(cat "$BACKUP_DIR/version.txt")"

echo ""
echo "=== Backup complete: $BACKUP_DIR ==="
echo "You can now run: openclaw update"
echo "If the dashboard goes offline, run:"
echo "  ~/.openclaw/scripts/post-update-restore.sh $BACKUP_DIR"

Post-Update Restore Script

Save this as ~/.openclaw/scripts/post-update-restore.sh:

#!/bin/bash
# Run AFTER updating OpenClaw if the dashboard is offline.
# Usage: ~/.openclaw/scripts/post-update-restore.sh [backup_dir]
# If no backup_dir given, uses the most recent backup.

set -e

if [ -n "$1" ]; then
    BACKUP_DIR="$1"
else
    BACKUP_DIR=$(ls -dt "$HOME/.openclaw/backups/"*/ \
                   2>/dev/null | head -1)
fi

if [ -z "$BACKUP_DIR" ] || [ ! -d "$BACKUP_DIR" ]; then
    echo "ERROR: No backup found. Run pre-update-backup.sh first."
    exit 1
fi

echo "=== OpenClaw Post-Update Restore ==="
echo "Using backup: $BACKUP_DIR"

# 1. Restore plist if it's missing or different
if [ -f "$BACKUP_DIR/ai.openclaw.gateway.plist" ]; then
    if ! diff "$BACKUP_DIR/ai.openclaw.gateway.plist" \
         ~/Library/LaunchAgents/ai.openclaw.gateway.plist \
         > /dev/null 2>&1; then
        echo "Plist changed/damaged — restoring from backup..."
        cp "$BACKUP_DIR/ai.openclaw.gateway.plist" \
           ~/Library/LaunchAgents/ai.openclaw.gateway.plist
        echo "✓ Plist restored"
    else
        echo "✓ Plist unchanged (ok)"
    fi
fi

# 2. Sync API keys into models.json
echo "Syncing API keys..."
python3 << 'EOF'
import json

with open(os.path.expanduser(
    '~/.openclaw/openclaw.json'), 'r') as f:
    real = json.load(f)
with open(os.path.expanduser(
    '~/.openclaw/agents/main/agent/models.json'), 'r') as f:
    models = json.load(f)

for provider in ['anthropic', 'deepseek',
                  'custom-api-deepseek-com']:
    if (provider in models.get('providers', {}) and
        provider in real.get('models', {}).get('providers', {})):
        real_key = real['models']['providers'][provider].get(
            'apiKey', '')
        if real_key and not real_key.startswith('YOUR_'):
            models['providers'][provider]['apiKey'] = real_key

with open(os.path.expanduser(
    '~/.openclaw/agents/main/agent/models.json'), 'w') as f:
    json.dump(models, f, indent=2)
print('✓ API keys synced to models.json')
EOF

# 3. Reinstall service and reload
echo "Reinstalling gateway service..."
openclaw gateway install --force 2>&1 || true

echo "Reloading service..."
launchctl bootout gui/$(id -u)/ai.openclaw.gateway \
    2>/dev/null || true
sleep 1
launchctl bootstrap gui/$(id -u) \
    ~/Library/LaunchAgents/ai.openclaw.gateway.plist

sleep 2

# 4. Verify
echo ""
echo "=== Checking status ==="
openclaw gateway status 2>&1

echo ""
echo "=== Restore complete ==="
echo "Dashboard: http://<your-ip>:18789/"

The Workflow

Once the scripts are in place, the update process becomes:

# 1. Always run this first
~/.openclaw/scripts/pre-update-backup.sh

# 2. Do the update
openclaw update
# or: brew upgrade openclaw

# 3. If the dashboard is offline after the update:
~/.openclaw/scripts/post-update-restore.sh

The restore script handles all failure modes automatically:

  1. Plist overwritten? → Restores from backup
  2. API keys desynced? → Syncs openclaw.json → models.json
  3. Service not running? → Reinstalls and reloads the LaunchAgent
  4. Not sure it worked? → Runs openclaw gateway status to verify
💡 Prevention tip: The scripts above fix the symptoms, but the permanent fix for API key corruption is one step at the source — resolve all $(security ...) patterns in ~/.openclaw/.env to real key values. This prevents the 401 recurrence entirely. See the API Key Corruption post for the one-liner fix.

Manual Recovery (No Scripts)

If you don't have the scripts yet and the dashboard is offline, here's the manual recovery sequence:

Step 1: Restore the plist

cp ~/Library/LaunchAgents/ai.openclaw.gateway.plist.backup \
   ~/Library/LaunchAgents/ai.openclaw.gateway.plist

This assumes you kept a backup copy of the plist. If you didn't, skip to step 3 and manually edit the fresh plist to add your port and environment variables.

Step 2: Sync API keys

python3 -c "
import json
with open('$HOME/.openclaw/openclaw.json') as f:
    real = json.load(f)
with open('$HOME/.openclaw/agents/main/agent/models.json') as f:
    models = json.load(f)
for p in ['anthropic','deepseek','custom-api-deepseek-com']:
    if (p in models.get('providers',{}) and
        p in real.get('models',{}).get('providers',{})):
        k = real['models']['providers'][p].get('apiKey','')
        if k and not k.startswith('YOUR_'):
            models['providers'][p]['apiKey'] = k
with open('$HOME/.openclaw/agents/main/agent/models.json',
          'w') as f:
    json.dump(models, f, indent=2)
print('Keys synced')
"

Step 3: Reinstall and reload

openclaw gateway install --force
launchctl bootout gui/$(id -u)/ai.openclaw.gateway 2>/dev/null
sleep 1
launchctl bootstrap gui/$(id -u) \
    ~/Library/LaunchAgents/ai.openclaw.gateway.plist

Step 4: Verify

openclaw gateway status

Look for Runtime: running and Connectivity probe: ok.

Hardening the Plist (Prevention)

While we can't stop openclaw gateway install --force from generating a fresh plist, we can make the plist more robust so it survives most issues. The most common fix: add a proper PATH to the environment variables.

Edit ~/Library/LaunchAgents/ai.openclaw.gateway.plist and add this inside the <dict> under EnvironmentVariables:

<key>PATH</key>
<string>/opt/homebrew/bin:/opt/homebrew/sbin:/usr/local/bin:\
/usr/bin:/bin:/usr/sbin:/sbin:$HOME/.local/bin:\
$HOME/.npm-global/bin:$HOME/bin</string>

This ensures the LaunchAgent can find openclaw, node, and any other tools it needs, even after an update changes the environment.

Important: After editing the plist, save a working copy as ai.openclaw.gateway.plist.backup in the same directory. This is your insurance policy — the restore script uses it as the source of truth.

How to Test (Without Breaking Anything)

Want to verify your backup and restore flow works before the next real update?

# 1. Run the backup
~/.openclaw/scripts/pre-update-backup.sh

# 2. Simulate a "bad" plist by renaming it
mv ~/Library/LaunchAgents/ai.openclaw.gateway.plist \
   ~/Library/LaunchAgents/ai.openclaw.gateway.plist.test

# 3. Run the restore (it'll see no plist and restore from backup)
~/.openclaw/scripts/post-update-restore.sh

# 4. Verify the dashboard is back
openclaw gateway status

Why This Matters

OpenClaw is a control plane. When it's offline, scheduled jobs don't run, Telegram messages go unanswered, email processing stops, and you lose access to your AI assistant. For anyone running OpenClaw as infrastructure (not a toy), an update that takes the dashboard offline is a real outage.

The backup-and-restore pattern here isn't unique to OpenClaw — it applies to any macOS LaunchAgent or Linux systemd service that stores custom configuration in a file that gets regenerated during updates. The principle is the same: identify the fragile file, back it up before mutation, and have a scripted restore path.

Ten seconds of prevention beats ten minutes of debugging. Every time.
