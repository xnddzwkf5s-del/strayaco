How I Shared My OpenClaw With My Family — With Lessons Learned

OpenClaw Multi-Agent Family AI Agent macOS Cloudflare

I run OpenClaw on a Mac mini at home. Recently I added my three children as users — each with their own isolated AI agent. This post walks through the architecture, configuration, and every mistake I made along the way. There's sample code for the key pieces, and notes for both humans and AI agents reading this.

What We Built

One OpenClaw Gateway, four agents:

macOS host
├── Agent: main    → Parent (existing)
├── Agent: child-1 → University student
├── Agent: child-2 → High school senior
└── Agent: child-3 → Younger student

Each child gets:

  • A Telegram bot — chat via Telegram Web on their notebook
  • A private file locker — upload documents through a browser (Cloudflare Tunnel + Access)
  • A personalised persona — each agent has unique SOUL.md, AGENTS.md, and teaching style
  • SQLite databases — journals, study trackers, XP logs
  • Expert panels — 5 sub-agents spawn for homework questions, cross-check answers

They share nothing. Separate workspaces, separate sessions, separate bots.

Step 1: Create the Agents

openclaw agents add child-1 --non-interactive --workspace ~/.openclaw/workspace-child-1
openclaw agents add child-2 --non-interactive --workspace ~/.openclaw/workspace-child-2
openclaw agents add child-3 --non-interactive --workspace ~/.openclaw/workspace-child-3

Lesson: Running these sequentially can overwrite each other because each reads the same stale config. Use --non-interactive flags, or patch openclaw.json manually after bulk creation. Always verify with openclaw agents list.

Step 2: Configure Telegram Bots

Each child creates a bot via @BotFather on Telegram. The tokens go into openclaw.json:

{
  "channels": {
    "telegram": {
      "accounts": {
        "default": { "botToken": "YOUR_BOT_TOKEN", "dmPolicy": "pairing" },
        "child-1": { "botToken": "CHILD_1_BOT_TOKEN", "dmPolicy": "pairing" },
        "child-2": { "botToken": "CHILD_2_BOT_TOKEN", "dmPolicy": "pairing" },
        "child-3": { "botToken": "CHILD_3_BOT_TOKEN", "dmPolicy": "pairing" }
      }
    }
  },
  "bindings": [
    { "agentId": "child-1", "match": { "channel": "telegram", "accountId": "child-1" } },
    { "agentId": "child-2", "match": { "channel": "telegram", "accountId": "child-2" } },
    { "agentId": "child-3", "match": { "channel": "telegram", "accountId": "child-3" } }
  ]
}

Lesson: Start with dmPolicy: "pairing". The child messages the bot, you run openclaw pairing approve telegram <CODE>, their ID is captured. Then switch to dmPolicy: "allowlist". Also: openclaw pairing approve automatically sets the paired user as command owner if commands.ownerAllowFrom is empty. Set that field FIRST.

Step 3: Write the Agent Personalities

Each agent gets a SOUL.md in its workspace. Example for a warm, confidence-building tutor:

# SOUL.md

## Teaching Style
1. Story-first — open every explanation with an analogy
2. Plain language — no jargon without defining it
3. Small wins — break everything into the tiniest possible first step

## Tone
- Never say "that's easy" — it dismisses effort
- Celebrate every line of code written
- "You're stuck? Good — that's where learning actually happens."

## Core Message
You believe in this student even when they don't believe in themselves.

And AGENTS.md controls behaviour — model switching, expert panels, workspace boundaries:

# AGENTS.md

## Model Switching
- Default: `deepseek-v4-flash` (fast, cheap)
- Switch to `deepseek-v4-pro` on homework keywords
- Use: `session_status(sessionKey="current", model="deepseek/deepseek-v4-pro")`

## Expert Panel Protocol
For homework questions, spawn 5 sub-agents in parallel:
1. Subject Expert — deep knowledge
2. Coding Expert — practical implementation
3. Education Expert — what the teacher is testing
4. Study Coach — learning strategy
5. Psychology Expert — emotional framing, encouragement

## Workspace Boundaries
- NEVER access paths outside your workspace
- All exec commands start with: `cd ~/.openclaw/workspace-child-1 && ...`

Step 4: Build a File Browser

Each child needs a place to upload documents. Here's the architecture:

Browser → Cloudflare Access (email OTP) → Cloudflare Tunnel → localhost:8091 → Python server

The Python server is ~400 lines, stdlib only. Three instances run as LaunchAgents:

<!-- ~/Library/LaunchAgents/com.child-1.filebrowser.plist -->
<dict>
    <key>Label</key><string>com.child-1.filebrowser</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/bin/python3</string>
        <string>/path/to/filebrowser/server.py</string>
    </array>
    <key>EnvironmentVariables</key>
    <dict>
        <key>BROWSER_PORT</key><string>8091</string>
        <key>BROWSER_ROOT</key><string>/path/to/workspace-child-1/documents</string>
    </dict>
    <key>RunAtLoad</key><true/>
    <key>KeepAlive</key><true/>
</dict>

Key security patterns in the server:

def safe_path(rel):
    """Resolve a path safely inside ROOT."""
    p = (ROOT / rel).resolve()
    try:
        p.relative_to(ROOT)       # ✅ Proper hierarchy check
        return p
    except ValueError:
        return None                # ❌ Traversal attempt blocked

# Upload handler — two-pass multipart parsing
MAX_UPLOAD = 50 * 1024 * 1024     # Server-side limit, not just JS
content_length = int(self.headers.get('Content-Length', 0))
if content_length > MAX_UPLOAD:
    self.send_json({'error': 'File too large'}, 413)
    return

# Two-pass: scan for dir field first, then extract file
# Handles any field ordering from the browser
for part in parts:
    if 'name="dir"' in header and 'filename=' not in header:
        subdir = part_content
    elif 'filename=' in header:
        file_data = (header, part_content)

# Filename sanitisation
filename = Path(raw_filename).name  # Strips ../ or leading /
dest = (dest_dir / filename).resolve()
dest.relative_to(ROOT)              # Re-validate after join

Lesson: cgi.FieldStorage fails silently on macOS Python 3.9. The manual multipart parser needed two passes — the first to collect the directory field, the second to extract the file. Order-independent parsing is essential because browsers don't guarantee FormData field order.

Lesson: str.startswith() for path containment is fragile. If ROOT is /data/agent and someone passes ../agent-other/secret, the string check passes. Always use Path.relative_to().

Step 5: Cloudflare Access

Three subdomains, each protected by email OTP:

child-1.example.com → localhost:8089
child-2.example.com → localhost:8090
child-3.example.com → localhost:8091

The Cloudflare tunnel config:

tunnel: family-tunnel
credentials-file: /path/to/credentials.json
ingress:
  - hostname: child-1.example.com
    service: http://localhost:8089
  - hostname: child-2.example.com
    service: http://localhost:8090
  - hostname: child-3.example.com
    service: http://localhost:8091
  - hostname: parent.example.com
    service: http://localhost:18789
  - service: http_status:404

Lesson: If you have an old cloudflared process from Homebrew (root-owned), it won't pick up new hostnames. Kill it. Manage cloudflared exclusively through LaunchAgent with KeepAlive: true. Verify with pgrep -l cloudflared — only ONE process.

Lesson: Cloudflare Access gates every request behind a session cookie. For the file browser's JavaScript, same-origin fetch() requests automatically send cookies — no special handling needed. But if API calls aren't appearing in DevTools Network tab at all, the JavaScript is broken, not the auth.

Step 6: JavaScript That Actually Works

The file browser spent hours broken because of this pattern:

// ❌ BROKEN — unescaped single quotes inside single-quoted JavaScript string
let links = '<a href="#" onclick="loadFiles('')">🏠 Home</a>';

// ✅ FIXED — use template literals (backticks) to avoid quote conflicts
let links = `<a href="#" onclick="loadFiles('')">🏠 Home</a>`;

The HTML is generated by Python, which adds another layer of escaping. The fix: use JavaScript template literals everywhere, and validate with:

# Extract JS from served HTML, check syntax
curl -s http://localhost:8091/ | python3 -c "
import sys
html = sys.stdin.read()
js = html[html.find('<script>')+8:html.find('</script>')]
open('/tmp/check.js','w').write(js)
"
node --check /tmp/check.js

Lesson: Python triple-quoted strings with inline JavaScript are a debugging nightmare. Serve static .js files. If inline is unavoidable, use backtick template literals and never escape ${}. Always run node --check after any change. If DevTools Network tab shows zero API calls, the JavaScript is broken — period.

Step 7: Backup Everything

# Pre-update backup script
tar -czf backup/workspace-child-1.tar.gz -C ~/.openclaw/workspace-child-1 .
tar -czf backup/workspace-child-2.tar.gz -C ~/.openclaw/workspace-child-2 .
tar -czf backup/workspace-child-3.tar.gz -C ~/.openclaw/workspace-child-3 .
cp ~/.openclaw/openclaw.json backup/
cp ~/.openclaw/.env backup/
cp -r ~/.cloudflared/ backup/
cp ~/Library/LaunchAgents/com.*.plist backup/

Each workspace is also a git repo — commit regularly and push to a private remote.

Key Takeaways

  1. OpenClaw's multi-agent routing is production-ready — bindings, workspaces, tool allowlists, Telegram accounts. It works.
  2. Cloudflare Tunnel + Access provides free, secure remote access without opening ports.
  3. Inline JavaScript in Python strings is a trap. Serve static files. Validate with node --check.
  4. Path containment must use Path.relative_to() — string prefix checks are a security vulnerability.
  5. Server-side validation always — client-side limits (file size, path checks) are suggestions, not enforcement.
  6. Test through the tunnel, not localhost — the user's path has Cloudflare, cookies, and browser quirks yours doesn't.
  7. One process, one manager — cloudflared, file browsers, everything through LaunchAgents. Kill anything else.
  8. Write comprehensive vault docs — troubleshooting, restart procedures, file paths. Your future self will thank you.
