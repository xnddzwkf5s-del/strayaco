Giving an AI Write Access to a Blogger Blog — Without Sharing a Password

Blogger API OAuth 2.0 Python AI Agents Security

Blogger's API key can only read. Here is the OAuth flow that lets an AI agent create drafts, edit them, and publish — with the blog owner approving exactly once and never sharing a password.

Why an API key cannot write

A Google API key identifies a project, not a person. It answers “which application is calling?” but not “who authorised this?”. For that reason Blogger's API key is read-only: it can fetch public posts, and nothing else.

CapabilityAPI keyOAuth 2.0
Read public postsYesYes
Create, edit, publish, deleteNoYes
Tied toA Google Cloud projectThe account owner's consent

Writing requires an access token minted from a refresh token. The refresh token is issued once, when the blog owner approves your application. The agent stores that token and exchanges it for a short-lived access token whenever it needs to call the API.

The flow in one picture

  1. You create an OAuth client in Google Cloud and download its JSON credentials.
  2. The blog owner opens a consent URL and approves the blogger scope.
  3. Google redirects to a loopback address with a one-time code.
  4. You exchange the code for a refresh token and store it with mode 600.
  5. Every API call refreshes an access token from that refresh token.

At no point does the agent see a password, a session cookie, or a two-factor code. The owner can revoke the grant at any time from their Google account, which invalidates the refresh token immediately.

Step 1 — Prepare the Google Cloud project

This is a one-time setup, about ten minutes. If a project already has the Blogger API enabled and a desktop OAuth client, reuse it.

  1. Open the Google Cloud Console and create a project, for example blog-publisher.
  2. Go to APIs & Services → Library, search for Blogger API v3, and enable it.
  3. Configure the OAuth consent screen (newer consoles call this Google Auth Platform). Choose External audience, set an app name and support email, and add the scope https://www.googleapis.com/auth/blogger.
  4. Add the blog owner's Google account under Audience → Test users. Only listed accounts can approve while the app is in testing.
  5. Go to Credentials → Create credentials → OAuth client ID and choose Desktop app. Download the JSON and keep it as client_secret.json.

Why “Desktop app”? That client type permits a loopback redirect (http://127.0.0.1:8765/) without pre-registering a URL, which is exactly what a local script needs. If you are forced to use “Web application”, add that loopback URL under Authorised redirect URIs.

The account that approves the consent becomes the author of every post the API creates. If the blog should show a different byline, approve from an account with that display name, or add a dedicated account as an administrator.

Step 2 — Capture the refresh token

The consent URL needs three parameters that are easy to miss:

  • access_type=offline — asks Google for a refresh token, not just an access token.
  • prompt=consent — forces the consent screen. Without it, a repeat authorisation silently returns no refresh token.
  • scope=https://www.googleapis.com/auth/blogger — one scope covers reading and writing posts.

On a machine with a browser, the script can listen on the loopback port and capture the code automatically. For an AI agent, the more reliable pattern is a manual handoff:

  1. The agent prints the consent URL and sends it to the owner.
  2. The owner approves. The browser is redirected to http://127.0.0.1:8765/?code=..., which fails to load because nothing is listening. That is expected; the URL bar still holds the grant.
  3. The owner saves that full URL into a text file and hands the file back.
  4. The agent exchanges the code for a refresh token.

Use a file, not chat. Consent codes are single-use and expire within minutes. Chat clients and agent runtimes often redact or truncate secret-shaped strings, and a truncated code cannot be exchanged. A file on disk avoids the problem entirely.

While the OAuth app remains in Testing status, Google expires refresh tokens after seven days. The next write then fails with invalid_grant, which means “re-consent”, not “wrong credentials”. Publishing the app to production makes the token durable, at the cost of a one-time “unverified app” warning during consent.

Step 3 — Store the token properly

The exchange produces three values: client ID, client secret, and refresh token. Store them together in token.json with mode 600, outside version control. On a server, environment variables are an acceptable alternative; on a laptop, the file is simpler.

chmod 600 client_secret.json token.json
echo "client_secret.json" >> .gitignore
echo "token.json" >> .gitignore

You also need the blog's numeric ID. Ask the API to resolve it from the public URL:

curl -s -H "Authorization: Bearer $ACCESS_TOKEN" \
  "https://www.googleapis.com/blogger/v3/blogs/byurl?url=https://yourblog.blogspot.com"

The response includes an id such as 1234567890123456789. That number, not the URL, identifies the blog in every write call.

Step 4 — The publisher script

The script below is deliberately small: three commands, standard library only, no browser automation. It creates a draft by default. Pass --live only when you mean it.

#!/usr/bin/env python3
"""Minimal Blogger API v3 publisher.

Three commands:
  auth   print the consent URL
  token  exchange a saved redirect URL for a refresh token
  post   create a draft (or publish) from Markdown/HTML

Examples:
  python3 blogger.py auth  --client client_secret.json
  python3 blogger.py token --client client_secret.json --redirect redirect.txt
  python3 blogger.py post  --token token.json --blog 1234567890123456789 \
      --title "Hello" --file hello.md
"""

import argparse
import json
import os
import sys
import urllib.error
import urllib.parse
import urllib.request
from pathlib import Path

AUTH = "https://accounts.google.com/o/oauth2/v2/auth"
TOKEN = "https://oauth2.googleapis.com/token"
API = "https://www.googleapis.com/blogger/v3"
SCOPE = "https://www.googleapis.com/auth/blogger"
REDIRECT = "http://127.0.0.1:8765/"


def client(path):
    block = json.loads(Path(path).expanduser().read_text())["installed"]
    return block["client_id"], block["client_secret"]


def cmd_auth(args):
    cid, _ = client(args.client)
    query = {
        "client_id": cid,
        "redirect_uri": REDIRECT,
        "response_type": "code",
        "scope": SCOPE,
        "access_type": "offline",
        "prompt": "consent",
    }
    print(f"{AUTH}?{urllib.parse.urlencode(query)}")


def cmd_token(args):
    cid, secret = client(args.client)
    text = Path(args.redirect).expanduser().read_text().strip()
    query = urllib.parse.parse_qs(urllib.parse.urlparse(text).query)
    code = query.get("code", [text])[0]
    data = urllib.parse.urlencode({
        "code": code,
        "client_id": cid,
        "client_secret": secret,
        "redirect_uri": REDIRECT,
        "grant_type": "authorization_code",
    }).encode()
    try:
        with urllib.request.urlopen(TOKEN, data=data, timeout=30) as resp:
            payload = json.load(resp)
    except urllib.error.HTTPError as exc:
        sys.exit(f"Exchange failed [{exc.code}]: {exc.read().decode()[:300]}")
    if "refresh_token" not in payload:
        sys.exit("No refresh_token returned — revoke access and retry the consent.")
    out = Path(args.out).expanduser()
    out.write_text(json.dumps({
        "client_id": cid,
        "client_secret": secret,
        "refresh_token": payload["refresh_token"],
    }, indent=2) + "
")
    os.chmod(out, 0o600)
    print(f"Wrote {out}")


def access_token(creds):
    data = urllib.parse.urlencode({
        "client_id": creds["client_id"],
        "client_secret": creds["client_secret"],
        "refresh_token": creds["refresh_token"],
        "grant_type": "refresh_token",
    }).encode()
    try:
        with urllib.request.urlopen(TOKEN, data=data, timeout=30) as resp:
            return json.load(resp)["access_token"]
    except urllib.error.HTTPError as exc:
        body = exc.read().decode()
        hint = " — re-run the consent" if "invalid_grant" in body else ""
        sys.exit(f"Token refresh failed [{exc.code}]{hint}: {body[:200]}")


def api(method, path, creds, body=None):
    request = urllib.request.Request(
        f"{API}{path}",
        data=json.dumps(body).encode("utf-8") if body is not None else None,
        method=method,
    )
    request.add_header("Authorization", f"Bearer {access_token(creds)}")
    if body is not None:
        request.add_header("Content-Type", "application/json; charset=utf-8")
    try:
        with urllib.request.urlopen(request, timeout=45) as resp:
            return json.load(resp)
    except urllib.error.HTTPError as exc:
        sys.exit(f"{method} {path} failed [{exc.code}]: {exc.read().decode()[:300]}")


def to_html(path, raw):
    if raw:
        return raw
    text = Path(path).expanduser().read_text(encoding="utf-8")
    if path.endswith((".md", ".markdown")):
        try:
            import markdown
        except ImportError:
            sys.exit("Markdown input needs: python3 -m pip install markdown")
        return markdown.markdown(text, extensions=["extra", "sane_lists"])
    return text


def cmd_post(args):
    creds = json.loads(Path(args.token).expanduser().read_text())
    body = {"kind": "blogger#post", "title": args.title,
            "content": to_html(args.file, args.html)}
    if args.labels:
        body["labels"] = [s.strip() for s in args.labels.split(",") if s.strip()]
    draft = "false" if args.live else "true"
    post = api("POST", f"/blogs/{args.blog}/posts/?isDraft={draft}", creds, body)
    print(json.dumps({"id": post.get("id"), "status": post.get("status"),
                      "url": post.get("url")}, indent=2))


def main():
    ap = argparse.ArgumentParser(description="Minimal Blogger API v3 publisher")
    sub = ap.add_subparsers(dest="cmd", required=True)

    p = sub.add_parser("auth")
    p.add_argument("--client", required=True)
    p.set_defaults(func=cmd_auth)

    p = sub.add_parser("token")
    p.add_argument("--client", required=True)
    p.add_argument("--redirect", required=True)
    p.add_argument("--out", default="token.json")
    p.set_defaults(func=cmd_token)

    p = sub.add_parser("post")
    p.add_argument("--token", required=True)
    p.add_argument("--blog", required=True)
    p.add_argument("--title", required=True)
    p.add_argument("--file")
    p.add_argument("--html")
    p.add_argument("--labels")
    p.add_argument("--live", action="store_true")
    p.set_defaults(func=cmd_post)

    args = ap.parse_args()
    args.func(args)


if __name__ == "__main__":
    try:
        main()
    except KeyboardInterrupt:
        sys.exit(130)

Install the optional Markdown dependency if you author posts as .md:

python3 -m pip install markdown

Then the full cycle looks like this:

# 1. Print the consent URL and send it to the owner
python3 blogger.py auth --client client_secret.json

# 2. Exchange the saved redirect URL for a refresh token
python3 blogger.py token --client client_secret.json --redirect redirect.txt

# 3. Create a draft
python3 blogger.py post --token token.json --blog 1234567890123456789 \
    --title "First post from the API" --file post.md --labels notes,api

# 4. Publish it once the draft has been reviewed
python3 blogger.py post --token token.json --blog 1234567890123456789 \
    --title "First post from the API" --file post.md --live

For a fuller workflow — listing posts, reading one back, patching a title, deleting — extend the same api() helper with GET, PATCH and DELETE. The endpoints are ordinary REST:

GET    /blogs/{blogId}/posts/{postId}
PATCH  /blogs/{blogId}/posts/{postId}
POST   /blogs/{blogId}/posts/{postId}/publish
DELETE /blogs/{blogId}/posts/{postId}

The draft-first rule

Drafts are free; corrections on a live post are visible to readers and can notify subscribers. The workflow that avoids embarrassment:

  1. Create a draft. The API returns its ID and status.
  2. Open it in Blogger. Check rendering, images, links, labels, and the byline.
  3. Patch what is wrong. Send only the fields that changed: title, content, or labels.
  4. Publish. Call posts/{id}/publish, then fetch the returned URL and confirm it loads.

One Blogger quirk is worth coding around: posts.get can return 404 for a draft that exists. Fall back to listing drafts with status=draft&fetchBodies=true and matching the ID in the response.

What the API cannot do

LimitationWorkaround
No image or file uploadUpload through the Blogger editor, or host images publicly and reference absolute HTTPS URLs
No theme, layout, comment or settings changesThose stay in the Blogger dashboard
No reliable post schedulingCreate the draft, schedule it in the UI
Post HTML is sanitisedScripts and some embeds are stripped; use inline styles and test in a draft
Author is the consenting accountConsent from the account whose byline should appear

The image limitation catches most people. The API accepts HTML, not multipart uploads, so a post that references local paths or private photo links will render broken for every reader.

Failure modes

SymptomMeaningFix
400 invalid_grantRefresh token expired or was revokedRe-run the consent; publish the app to production if this keeps happening weekly
403 access_deniedThe account is not a test user, or the app is unverifiedAdd the account under Test users, or choose Advanced → continue on the warning
403 on write, read worksThe account is only a readerGrant Owner, Admin or Author on the blog
401Token belongs to another account, or was revokedRe-consent and confirm which account approved
404 on a draftBlogger does not return drafts reliably from posts.getList drafts and match the ID
No refresh token returnedConsent lacked prompt=consent, or a grant already existedRevoke at myaccount.google.com/permissions and retry
Wrong blog updatedThe numeric blog ID points elsewhereRe-resolve it with blogs/byurl

Security rules

  • Treat the refresh token like a password. It grants full write access to the blog. Mode 600, never in git, never pasted into chat.
  • Prefer a dedicated Google account. Add it as a blog administrator and consent from it. Revoking access is then one click and does not disturb a personal account.
  • Delete is permanent. Blogger has no trash for API deletions. Keep the source Markdown in version control as the real archive.
  • Ask before publishing. An agent with a token can publish instantly; the draft-first rule is what keeps a bad sentence off the front page.
  • Strip personal data. No addresses, booking references, passport numbers, phone numbers, or live location in posts. Remove EXIF from photos before uploading.

The takeaway

Giving an AI write access to a blog is not a matter of finding the right API key — it is a matter of delegating one narrow permission and handling the token like a credential. The owner approves once, keeps their password, and can revoke the grant at any time. The agent gets exactly what it needs: the ability to draft, edit, and publish, with a human reviewing the last step.

That is a better security model than sharing a login, and a better workflow than automating a browser.
