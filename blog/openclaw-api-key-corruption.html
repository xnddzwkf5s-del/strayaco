OpenClaw API Key Corruption: Anatomy of a Silent 401

OpenClaw macOS launchd Security DevOps Debugging

Your AI agent stops responding. Model switches fail silently. Cron jobs that ran reliably for weeks start returning errors. You check your config file — the API key is there, 35 characters, correct. You test it directly with curl — 200 OK. But the gateway keeps logging 401 Authentication Fails.

This is the story of a particularly insidious bug: how macOS launchd silently poisons your API keys with shell injection artifacts, why nothing in your config shows it, and how to fix it permanently.

TL;DR: OpenClaw's service installer writes keys using $(security find-generic-password) shell substitution, but launchd doesn't expand $() — it sends the literal string (including  -w)) as your API key. The fix: write real key values directly into the service environment file, never rely on shell command substitution in plist EnvironmentVariables.

The Symptom: Everything Looks Right, Nothing Works

Here's what you'll see when this bug hits:

  • Switching to any affected model: no response, silent failure (no visible error in the dashboard — the agent simply produces nothing)
  • Scheduled cron jobs using that model: fail with 401
  • Error in gateway logs: 401 Authentication Fails, Your api key: **** -w) is invalid — the -w) suffix is the smoking gun
  • Error hash is consistent across failures: sha256:b6c634fc9b1e
  • Models from other providers (Anthropic, OpenAI) using different keys in the same environment: continue working normally

The most confusing part: a direct curl test with the key from openclaw.json returns 200. The config file is correct. The keychain is correct. Only the running gateway process has the wrong key.

Root Cause: launchd Does Not Expand Shell

OpenClaw's service installer (openclaw gateway install) writes API keys into the service environment file at:

~/.openclaw/service-env/ai.openclaw.gateway.env

For keys listed in OPENCLAW_SERVICE_MANAGED_ENV_KEYS, the installer pulls values from the macOS keychain using shell command substitution:

export DEEPSEEK_API_KEY=$(security find-generic-password -s DEEPSEEK_API_KEY -w)

Or worse, the literal $() string is written into the LaunchAgent plist's EnvironmentVariables dictionary:

<key>DEEPSEEK_API_KEY</key>
<string>$(security find-generic-password -s DEEPSEEK_API_KEY -w)</string>

launchd on macOS does not expand $() in plist EnvironmentVariables. It treats the entire string as a literal value. The DeepSeek API key sent to the provider becomes:

sk-xxxxxxxx...xxxx -w)

Note the trailing space and -w) — that's the shell flag and closing parenthesis from the security command, now permanently fused to your API key.

Every diagnostic tool you'd naturally reach for shows the correct key. Only the runtime process environment reveals the corruption — and even then, you have to know to look.

How the Gateway Resolves Keys (Priority Chain)

Understanding the resolution order is critical to fixing this. When the gateway starts, it checks for API keys in this sequence — and the first one wins:

1. Service env file: ~/.openclaw/service-env/ai.openclaw.gateway.env ← WINS
2. LaunchAgent plist: EnvironmentVariables dictionary
3. openclaw.json: models.providers.{name}.apiKey
4. agent/models.json: auto-patched by launchd WatchPath

This means you can have a perfectly valid key in openclaw.json (layer 3), but if the env file or plist (layers 1-2) contain a corrupted value, that's what the gateway actually uses. The config file never gets consulted.

This priority chain is normal for OpenClaw and isn't a bug in itself — it's the standard way environment variables override config files. The bug is specifically that the installer writes a non-expandable shell command as the environment value.

The Recovery: Fix It in One Shot

Automated recovery (recommended)

Run the recovery script (create it first if you don't have it):

bash ~/.openclaw/scripts/fix-openclaw-api-keys.sh

This script:

  1. Extracts real keys from openclaw.json
  2. Strips any $() shell commands from the env file
  3. Writes literal key values directly into the env file
  4. Syncs keys to models.json
  5. Restarts the gateway
  6. Verifies with direct API calls

Manual recovery (step by step)

Step 1: Extract the real key from config

python3 -c "import json; print(json.load(open('$HOME/.openclaw/openclaw.json'))['models']['providers']['deepseek']['apiKey'])"

Copy the output — this is your real key (should be ~35 characters, no spaces, no -w)).

Step 2: Check for shell injection in the env file

grep '\$(' ~/.openclaw/service-env/ai.openclaw.gateway.env

If you see any $() in the output — those lines need to be replaced with literal values.

Step 3: Write real key directly into the env file

# Replace the shell command with a literal key value
# Edit ~/.openclaw/service-env/ai.openclaw.gateway.env and change:
#   export DEEPSEEK_API_KEY=$(security find-generic-password ...)
# To:
#   export DEEPSEEK_API_KEY='sk-your-real-35-char-key-here'

# Or use this one-liner (substitute your real key):
python3 -c "
import re
key = 'sk-your-real-key-here'
with open('$HOME/.openclaw/service-env/ai.openclaw.gateway.env','r') as f:
    c = f.read()
c = re.sub(r'export DEEPSEEK_API_KEY=.*', f\"export DEEPSEEK_API_KEY='***'\", c)
with open('$HOME/.openclaw/service-env/ai.openclaw.gateway.env','w') as f:
    f.write(c)
print('Done')
"

Step 4: Also check the plist

plutil -p ~/Library/LaunchAgents/ai.openclaw.gateway.plist | grep -A5 EnvironmentVariables | grep '\$('

If this returns anything, the plist itself has shell injection. Fix it by editing the plist and replacing the $() with the real key, or re-run openclaw gateway install after fixing the env file.

Step 5: Restart and verify

openclaw gateway restart
sleep 10

# Test the key directly
curl -s -o /dev/null -w "%{http_code}" \
  -X POST https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer YOUR_REAL_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-chat","max_tokens":5,"messages":[{"role":"user","content":"hi"}]}'
# Should return: 200

Permanent Defenses

After fixing the immediate issue, deploy these four defenses to prevent recurrence:

DefenseLocationWhat It Does
Direct env keys~/.openclaw/service-env/ai.openclaw.gateway.envReal key values — no $() shell commands, no plist indirection
fix-models-keys.sh~/.openclaw/scripts/Patches placeholder keys in models.json after updates
launchd WatchPath~/Library/LaunchAgents/local.openclaw.fix-models-keys.plistAutomatically fires fix-models-keys.sh when models.json changes
Recovery script~/.openclaw/scripts/fix-openclaw-api-keys.shOne-shot fix for all key corruption issues

Prevention Rules (Tattoo These)

  1. NEVER rely solely on openclaw config set models.providers.{name}.apiKey — it only writes openclaw.json, which is layer 3 in the priority chain
  2. ALWAYS write API keys directly into ~/.openclaw/service-env/ai.openclaw.gateway.env as literal values in export KEY='value' format
  3. ALWAYS test with a direct curl after any key change
  4. ALWAYS restart the gateway after changing keys
  5. NEVER use $() shell commands in plist EnvironmentVariables — launchd doesn't expand them
  6. NEVER use $() shell commands in the service env file for key values

Why This Matters Beyond OpenClaw

This bug is a case study in environment-vs-config desync — a class of failure that's notoriously hard to debug because every tool you check shows the correct value, but the runtime reads from a different source.

The pattern applies broadly:

  • systemd on Linux: EnvironmentFile= directives have similar shell expansion rules — know whether your unit is expanding or reading literally
  • Docker: --env-file vs docker-compose.yml environment: vs secrets — three layers, each with different expansion behavior
  • Kubernetes: ConfigMaps vs Secrets vs envFrom — none expand $(), but some expand $(VAR) references
  • CI/CD pipelines: GitHub Actions secrets, GitLab CI variables, env-file sourcing — each runner has its own shell behavior

The lesson: know the resolution order of your config layers, and never assume shell expansion works in a non-shell context. Environment variables in plists, YAML, and systemd units are literal strings unless explicitly documented otherwise.

Key takeaway: When debugging "works from CLI but not from service" problems, the answer is almost always in the environment. Use ps eww (macOS) or /proc/PID/environ (Linux) to inspect what the running process actually sees — not what you think it should see.
