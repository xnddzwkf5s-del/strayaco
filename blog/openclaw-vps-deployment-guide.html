🧑 Human — VPS & Security Setup

You're about to create a tiny Linux server in the cloud that will run your AI agent 24/7. This section covers everything from clicking "Create Droplet" to locking down SSH so only you (and your recovery console) can get in. Follow every step in order — skipping ahead is how people get locked out.

1. Create Your DigitalOcean Droplet

Head to cloud.digitalocean.com, log in (or sign up — you get $200 free credit for 60 days), and click the green Create Droplet button. Configure as follows:

  • Region: Sydney (syd1) — closest to Australia, lowest latency for us
  • Image: Ubuntu 24.04 LTS
  • Size: Basic, Regular, $6/mo (1 GB RAM, 1 vCPU, 25 GB SSD)
  • Authentication: SSH Key (skip password — we'll add your key)
  • Hostname: Something memorable, like openclaw-agent

If you haven't added an SSH key yet, click New SSH Key. Open your local terminal and run:

# Generate a new key if you don't have one (press Enter for defaults)
ssh-keygen -t ed25519 -C "your-email@example.com"

# Copy the public key to paste into DigitalOcean
cat ~/.ssh/id_ed25519.pub

Copy the output starting with ssh-ed25519 and paste it into the DigitalOcean box. Then click Create Droplet.

Wait about 30 seconds. Once it's running, you'll see an IP address (e.g. 165.232.45.100). Copy that IP — you'll use it constantly.

2. First Login as Root

From your local machine, SSH in as root using your key:

ssh root@YOUR_DROPLET_IP

You should connect without a password prompt. If it asks for a password, something is wrong with your key setup — go back and check the DigitalOcean SSH key section. If you see a warning about "ECDSA host key" or "authenticity of host," type yes and press Enter.

3. Create a Non-Root User

Root is too powerful for daily use. One mistake as root can destroy your server. Create a regular user with sudo privileges instead:

# Create a new user (replace 'pang' with your preferred username)
adduser pang

# You'll be prompted for a password — use a strong one, different from any other password you use
# Full name, room number, etc. can just be left blank (press Enter)

# Give the user sudo (admin) privileges
usermod -aG sudo pang

4. Copy Your SSH Key to the New User

The new user needs your SSH key to log in. While still logged in as root:

# Copy root's authorized keys to the new user
cp -r ~/.ssh /home/pang/.ssh
chown -R pang:pang /home/pang/.ssh
chmod 700 /home/pang/.ssh  # Only user can read/write/execute
chmod 600 /home/pang/.ssh/authorized_keys  # Only user can read/write

Now open a second terminal window (keep the root session alive!) and test the new user login:

ssh pang@YOUR_DROPLET_IP

If it works without a password, you're golden. If it doesn't work, don't proceed — troubleshoot and fix this first.

5. ⚠️ Booby Trap — The Biggest Lesson

Before you lock SSH down, open a third terminal window and SSH in as your new user. Keep it sitting there with a shell prompt. I'm serious. You'll understand why in a moment.

This "live backup session" is your insurance policy. If you misconfigure something in the next steps and lock yourself out, that session is still open and you can fix things. Without it, you'd need to use the DigitalOcean recovery console (more on that later).

6. Harden SSH Configuration

Ubuntu 24.04 changed how SSH config works. The old method of editing /etc/ssh/sshd_config directly still works, but the cleaner approach is to use a drop-in file. The system reads everything in /etc/ssh/sshd_config.d/ in alphabetical order, and later files override earlier ones.

Run these commands as pang with sudo:

# Create a drop-in config file (numbers ensure it runs after defaults)
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf > /dev/null << 'EOF'
# Disable root login — reduces attack surface enormously
PermitRootLogin no

# Only allow key-based authentication (no passwords at all)
PasswordAuthentication no
KbdInteractiveAuthentication no

# Use only Ed25519 keys (most secure, most modern)
PubkeyAcceptedKeyTypes ssh-ed25519

# Limit login attempts to prevent brute force
MaxAuthTries 3

# Only allow your specific user to SSH in
AllowUsers pang
EOF

This file disables root login, turns off password auth entirely (including the newer KbdInteractiveAuthentication), restricts key types to Ed25519 only, limits auth retries, and whitelists only your user.

Now the critical moment. Test before committing.

# First, check that the SSH config is valid
sudo sshd -t

# If this prints nothing, the config is good. If it prints an error, fix it.
# Common errors: typos in parameter names, missing values, unsupported key types

# Now reload the SSH daemon — but leave your backup session open!
sudo systemctl reload sshd

Stop right here. Before closing anything, test from your backup terminal session that SSH still works. Run a command or just check the prompt is alive. The reload command doesn't kill existing sessions, so your three windows should all still be connected.

Now close your original root session (type exit). Then from a brand new terminal window, try logging in as your new user:

ssh pang@YOUR_DROPLET_IP

If it connects successfully, you're done with SSH hardening. If it fails:

  • Use your still-open backup session to check sudo sshd -t for errors
  • Fix the config in /etc/ssh/sshd_config.d/99-hardening.conf
  • Run sudo systemctl reload sshd again
  • Try the new terminal login again

Never, ever run systemctl reload sshd or restart sshd without an active backup SSH session ready to repair things. This is the #1 way people lose access to their servers.

7. Firewall — UFW

Your droplet starts with all ports open. That's like leaving your front door unlocked. Let's fix that:

# Allow SSH (port 22), HTTP (port 80), HTTPS (port 443) only
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Enable the firewall (it will warn you — say yes)
sudo ufw enable

# Check the status
sudo ufw status verbose

You should see three allowed ports (22, 80, 443) and everything else denied by default. If you can't see port 22 allowed, do not close your SSH session — re-run the allow command first.

8. fail2ban — Extra Brute-Force Protection

Even though we disabled password authentication (which already kills most brute force), fail2ban adds a safety net. It monitors SSH logs and temporarily bans IPs that show suspicious behaviour:

# Install fail2ban
sudo apt update
sudo apt install fail2ban -y

# Create a local config (don't edit the default jail.conf — it gets overwritten on updates)
sudo tee /etc/fail2ban/jail.local > /dev/null << 'EOF'
[DEFAULT]
# Ban for 1 hour
bantime = 1h
# After 5 failed attempts
maxretry = 5
# Within a 10 minute window
findtime = 10m

[sshd]
enabled = true
# Only log authentication failures
logpath = %(sshd_log)s
EOF

# Restart to apply
sudo systemctl restart fail2ban

# Check it's running
sudo fail2ban-client status sshd

With key-only SSH enabled, fail2ban will almost never trigger for legitimate users. But it protects against a worst case — if someone finds a way to bypass your key config or if a future software bug exposes password auth, fail2ban is there. It costs nothing to run.

Check the banned IP list occasionally:

sudo fail2ban-client status sshd

🤖 AI — Execute After Human Setup

The human has created the droplet, set up a non-root user with SSH key access, hardened SSH, enabled UFW, and installed fail2ban. Now it's your turn to verify everything is correct and set up the application environment.

1. Verify SSH Security

Connect as the non-root user and confirm all hardening is in place:

# Connect to the server
ssh pang@{DROPLET_IP}

# Verify root login is disabled
sudo sshd -T | grep permitrootlogin
# Expected: permitrootlogin no

# Verify password auth is disabled
sudo sshd -T | grep passwordauthentication
# Expected: passwordauthentication no

# Verify only Ed25519 keys are accepted
sudo sshd -T | grep pubkeyacceptedkeytypes
# Expected: includes ssh-ed25519 only

# Verify the drop-in file exists and is correct
cat /etc/ssh/sshd_config.d/99-hardening.conf
# Should show: PermitRootLogin no, PasswordAuthentication no, AllowUsers pang

2. Verify UFW Rules

sudo ufw status verbose
# Expected output:
# Status: active
# Logging: on (low)
# Default: deny (incoming), allow (outgoing), disabled (routed)
# New profiles: skip
#
# To                         Action      From
# --                         ------      ----
# 22/tcp                     ALLOW IN    Anywhere
# 80/tcp                     ALLOW IN    Anywhere
# 443/tcp                    ALLOW IN    Anywhere

If port 22 is missing from the list, stop immediately — adding UFW rules without SSH access will lock you out. Run sudo ufw allow 22/tcp before proceeding.

3. Verify fail2ban

sudo fail2ban-client status sshd
# Expected: Status shows "Currently banned: 0" and "Total banned: 0" initially

# Check fail2ban is actively monitoring
sudo tail -f /var/log/fail2ban.log &
# You should see: "Started fail2ban.2" or "Starting jail 'sshd'"

4. Install Dependencies

# System packages
sudo apt update
sudo apt upgrade -y

# Install essential tools
sudo apt install -y curl wget git ufw python3 python3-pip python3-venv

# PostgreSQL (NOT SQLite — see the development principles)
sudo apt install -y postgresql postgresql-contrib
sudo systemctl start postgresql
sudo systemctl enable postgresql

5. Set Up the Application Directory

# Create the application directory
sudo mkdir -p /opt/openclaw

# Create a dedicated user for the application
sudo adduser --system --group --no-create-home openclaw

# Set ownership
sudo chown -R openclaw:openclaw /opt/openclaw
sudo chmod 750 /opt/openclaw

6. ⚠️ Create .env File — Critical Security

This is one of the most important security steps. Your .env file will contain API keys, database passwords, and secrets. The permissions must be 640 with group www-data, not 644 (which is world-readable).

If you use a single-tenant OpenClaw setup (domain + Caddy reverse proxy), 640 with user-only access is fine. But if you ever need your web server to read environment variables (e.g. for a multi-service deployment), use the www-data group approach below.

# Create the .env file with restricted permissions from the start
sudo touch /opt/openclaw/.env

# Set ownership: root owns the file, www-data group can read it
sudo chown root:www-data /opt/openclaw/.env

# Set permissions: 640 = owner (root) can read/write, group (www-data) can read, others get nothing
sudo chmod 640 /opt/openclaw/.env

# Verify permissions
ls -la /opt/openclaw/.env
# Expected: -rw-r----- 1 root www-data ... .env
#                                            ^
#   NEVER: -rw-r--r-- (644 = world readable = API keys exposed)
#   NEVER: -rw------- (600 = root only, breaks if other services need it)

The difference between 640 and 644 is the difference between "a data breach" and "not a data breach." With 644, any process on the server (including a compromised nginx worker, a malicious npm package in a client project, or a misconfigured backup script) can read your secrets. With 640, only root and the www-data group can. Keep it that way.

Write the environment variables:

# Edit the file
sudo nano /opt/openclaw/.env

# At minimum you'll need:
OPENCLAW_API_KEY=your-api-key-here
DATABASE_URL=postgresql://openclaw:password@localhost:5432/openclaw
OPENAI_API_KEY=sk-your-openai-key
# ... plus any other secrets your agent needs

7. 🚨 Deployment Verification — Non-Negotiable

After every configuration change or code deployment, run these checks. Do not skip them. Do not assume rsync "probably worked." The AI agent has no human intuition — it needs cold, hard verification.

7a. Rsync Best Practices

When deploying files to the server, always use explicit full destination paths, not directory targets. Rsync has a dangerous behaviour: if you sync a single file to a directory path, it strips the subdirectory structure.

# ✅ CORRECT — use full destination file path
rsync -avz --checksum app/templates/index.html pang@{DROPLET_IP}:/opt/openclaw/app/templates/index.html

# ❌ WRONG — using directory target strips subdirectories
# rsync -avz app/templates/index.html pang@{DROPLET_IP}:/opt/openclaw/app/templates/
# This would create /opt/openclaw/app/templates/index.html/index.html

# ✅ For bulk deploys, use directory sources
rsync -avz --checksum app/templates/ pang@{DROPLET_IP}:/opt/openclaw/app/templates/

# Always use --checksum for rewritten files to bypass timestamp comparison
# Without it, rsync may silently skip files if mtimes happen to match

7b. Post-Deploy Verification

# 1. Check file was actually deployed
ssh pang@{DROPLET_IP} "ls -la /opt/openclaw/.env"
# Expected: file exists, permissions are 640

# 2. Check line counts (if you rewrote a file, line count should match)
ssh pang@{DROPLET_IP} "wc -l /opt/openclaw/.env"
# Expected: matches the source file line count

# 3. Grep for a unique marker from the new version
ssh pang@{DROPLET_IP} "grep 'UNIQUE_MARKER_FROM_NEW_VERSION' /opt/openclaw/.env"
# Expected: non-empty output (shows the line was deployed)

# 4. Check HTTP status codes
curl -s -o /dev/null -w "%{http_code}" http://localhost:80
# Expected: 200

# 5. Check HTTPS (if deployed)
curl -s -o /dev/null -w "%{http_code}" https://your-domain.com
# Expected: 200 or 301/302

8. Escape Hatch — DigitalOcean Recovery Console

Despite all precautions, you may eventually lock yourself out. Maybe you fat-fingered the UFW default policy, or a config file has a syntax error that the reload accepted but reboot didn't. The DigitalOcean recovery console is your universal escape hatch.

How to access it:

  1. Log in to cloud.digitalocean.com
  2. Click Droplets in the left sidebar
  3. Click your droplet name
  4. In the top-right, click Console (or Access → Launch Console on newer dashboards)
  5. A browser-based terminal will open — you'll be prompted for your non-root username and password

What you can fix from the recovery console:

  • If UFW blocked port 22: sudo ufw allow 22/tcp
  • If SSH config is broken: sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
  • If fail2ban banned your IP: sudo fail2ban-client set sshd unbanip YOUR_IP
  • If .env permissions are wrong: sudo chmod 640 /opt/openclaw/.env
  • If services are down: sudo systemctl restart sshd or sudo reboot

Pro tip: Test the recovery console now, while everything is working. Open it up, log in, poke around, then close it. You don't want to be learning the interface for the first time when you're panicking because you're locked out.

🧑 Human — OpenClaw Installation & Configuration

OpenClaw is a Node.js application that runs as a background service (called the Gateway) on your VPS. It connects your chat channels (Telegram, webchat, etc.) to large language models like DeepSeek, Claude, and Ollama. Think of it as a smart switchboard — it routes messages from your family's phones through AI models and back to you, all while keeping your data on your own server.

Step 1: Install Node.js

OpenClaw requires Node.js v22 or later. DigitalOcean's Ubuntu 24.04 LTS ships with an older version, so you'll need the NodeSource repository:

# Install Node.js 22 LTS
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash -
sudo apt-get install -y nodejs

# Verify
node --version   # Should show v22.x.x
npm --version    # Should show 10.x.x

Step 2: Install OpenClaw globally

sudo npm install -g openclaw

# Verify installation
openclaw --version   # e.g. 2026.5.19

The -g flag installs OpenClaw globally so the openclaw command is available in your PATH. On Ubuntu, global npm packages go to /usr/lib/node_modules/.

⚠️ macOS users: If you use Homebrew, note that brew upgrade openclaw only updates the Homebrew cask (the launcher script). The actual CLI runtime lives in npm's global space. Always run npm update -g openclaw to get the latest CLI version. The two can drift apart — run openclaw --version to check which one you actually have.

Step 3: Initialise the config

OpenClaw stores everything under ~/.openclaw/. You can bootstrap with the guided wizard, or create the file manually. The guided approach is recommended for first-time setup:

openclaw setup

This creates the default config file at ~/.openclaw/openclaw.json and a workspace directory at ~/.openclaw/workspace/.

Step 4: Install the Gateway as a systemd service

The Gateway is the heart of OpenClaw — it's the WebSocket server that listens for messages from your chat channels and routes them through the AI models. You want it to start automatically when your VPS boots and restart if it crashes:

openclaw gateway install

# Expected output:
#   Created symlink /etc/systemd/system/default.target.wants/openclaw-gateway.service
#   Systemd service installed. Run: sudo systemctl start openclaw-gateway

# Start it now
sudo systemctl start openclaw-gateway

# Check it's running
sudo systemctl status openclaw-gateway

# Enable auto-start on boot
sudo systemctl enable openclaw-gateway

The openclaw gateway install command creates a systemd unit file at /etc/systemd/system/openclaw-gateway.service. It runs the Gateway as your current user (not root), which is important for file permissions on your config and workspace.

Step 5: Run the health checker

openclaw doctor

The doctor command scans your entire setup — config structure, API key presence, Gateway connectivity, plugin health, and channel state. It flags missing keys, misconfigured providers, and common pitfalls. Run it whenever something doesn't work, or add --fix to auto-repair where possible:

openclaw doctor --fix

Key fields per provider:

  • models — An array of model definitions. Each model has an id (used in routing), a contextWindow (maximum tokens it can process), and reasoning (whether it supports chain-of-thought thinking).

B. API Key Security — Read This Carefully

You have two options for API keys:

Option 1: Inline in config (simplest, works everywhere)

Put the key directly in the apiKey field in openclaw.json. This is fine as long as you don't check the file into a public Git repo. The file permissions should be 600 (owner read/write only):

chmod 600 ~/.openclaw/openclaw.json

Option 2: Environment variables (for shared config files)

OpenClaw reads a .env file from ~/.openclaw/.env. If you want to keep API keys out of openclaw.json, add variables there:

# ~/.openclaw/.env — keep this file 600 (owner rw only)
DEEPSEEK_API_KEY=sk-your-deepseek-key
ANTHROPIC_API_KEY=sk-ant-your-anthropic-key
TELEGRAM_BOT_TOKEN=your-bot-token
GATEWAY_AUTH_TOKEN=your-gateway-token
🚨 CRITICAL: Never use shell substitution in .env files.

Do NOT do this:
DEEPSEEK_API_KEY=$(security find-generic-password ...)

OpenClaw reads .env as plain key=value pairs. Shell backticks, $() expansion, and command substitution are not evaluated. The literal string $(security ...) will be used as your API key, which will fail every request.

If you need to resolve a key from a secret manager, resolve it first, then write the resolved value into .env or directly into the config. For example:
echo "DEEPSEEK_API_KEY=$(security find-generic-password -s openclaw-deepseek -w)" > ~/.openclaw/.env

The shell expansion happens when you write the file, not when OpenClaw reads it.

C. Agent Configuration

Each "agent" is a personality/profile that routes messages through specific models. You have one main agent (your own) and can create separate agents for family members. Each agent has its own workspace, model preferences, and skill set.

{
  "agents": {
    "defaults": {
      "model": {
        "primary": "deepseek/deepseek-v4-flash",
        "fallbacks": [
          "deepseek/deepseek-reasoner"
        ]
      },
      "models": {
        "deepseek/deepseek-v4-flash": {
          "alias": "deepseek-v4-flash",
          "params": {
            "max_tokens": 384000,
            "timeout": 300000,
            "max_retries": 3
          }
        },
        "deepseek/deepseek-reasoner": {
          "alias": "deepseek-reasoner",
          "params": {
            "max_tokens": 64000,
            "timeout": 120000,
            "max_retries": 3
          }
        },
        "anthropic/claude-sonnet-4-6": {
          "alias": "claude-sonnet-4-6"
        }
      }
    },
    "list": [
      {
        "id": "main",
        "model": {
          "primary": "deepseek/deepseek-v4-flash"
        }
      },
      {
        "id": "agent-family-1",
        "name": "Family Member",
        "workspace": "/home/ubuntu/.openclaw/workspace-melinda",
        "model": {
          "primary": "deepseek/deepseek-v4-flash"
        }
      }
    ]
  }
}

Key concepts:

  • Primary model — The default model used for conversations. Format: provider/model-id.
  • Fallbacks — If the primary model is unavailable (API down, rate limited), OpenClaw automatically tries the fallback in order. This keeps your agents running even during outages.
  • Model aliases — Short, human-readable names for your models. Instead of typing deepseek/deepseek-v4-flash, you can reference it as deepseek-v4-flash. Aliases make the config easier to read and change.
  • Per-model params — Each model can have custom max_tokens, timeout (in ms), and max_retries. Fast models like V4 Flash can have short timeouts; reasoning models like DeepSeek Reasoner may need longer ones.

D. Channels — Telegram Bot Setup

Channels are how your family talks to their agents. Telegram is the most popular — create one bot per family member using @BotFather on Telegram, then configure each one:

{
  "channels": {
    "telegram": {
      "enabled": true,
      "accounts": {
        "default": {
          "botToken": "YOUR_TELEGRAM_BOT_TOKEN",
          "dmPolicy": "pairing",
          "allowFrom": ["1234567890"]
        },
        "agent-family-1": {
          "botToken": "TELEGRAM_BOT_TOKEN_AGENT_1",
          "dmPolicy": "allowlist",
          "allowFrom": ["1234567890"],
          "groupAllowFrom": ["1234567890"]
        },
        "agent-family-3": {
          "botToken": "TELEGRAM_BOT_TOKEN_AGENT_2",
          "dmPolicy": "allowlist",
          "allowFrom": ["1234567890"],
          "groupAllowFrom": ["1234567890"]
        }
      }
    }
  }
}

Each bot account gets its own Telegram bot token (created via @BotFather). Fields explained:

  • dmPolicy — pairing means users request pairing and you approve. allowlist means only specific Telegram user IDs can message the bot.
  • allowFrom — Telegram user IDs (numeric) that are allowed to DM this bot. Get a user's ID by messaging @userinfobot on Telegram.
  • groupAllowFrom — Same concept but for group chats where the bot is added.

To get your Telegram user ID, message the @userinfobot on Telegram. It will reply with your numeric ID — save that number.

E. Gateway — Port, Binding, and Auth

The Gateway is your OpenClaw server's network front door. You control who can connect and how:

{
  "gateway": {
    "port": 18789,
    "mode": "local",
    "bind": "lan",
    "auth": {
      "mode": "token",
      "token": "your-generated-secret-token",
      "rateLimit": {
        "maxAttempts": 10,
        "windowMs": 60000,
        "lockoutMs": 300000
      }
    },
    "controlUi": {
      "allowedOrigins": [
        "http://localhost:18789",
        "http://192.168.1.100:18789",
        "https://your-domain.com"
      ]
    },
    "trustedProxies": [
      "127.0.0.1",
      "::1"
    ]
  }
}

Key settings:

  • port — Default is 18789. Pick any unused port. You'll need to open this in your VPS firewall if accessing remotely.
  • bind — Controls network interface: loopback (local only, safest), lan (local network), tailnet (Tailscale network), custom (manual interface). For a VPS that you access remotely, you'll likely use a reverse proxy (like nginx + Cloudflare) rather than binding to the public interface directly.
  • auth.mode — token requires a shared secret on every WebSocket connection. password is similar. none is only safe on loopback. Always use a token on a VPS.
  • rateLimit — Prevents brute-force attacks: 10 attempts per 60-second window, then lock out for 5 minutes.
  • controlUi.allowedOrigins — CORS restrictions for the web dashboard. Only listed domains can load the Control UI. Add your VPS's LAN IP and public domain here.
  • trustedProxies — IPs that are allowed to set the X-Forwarded-For header. Include your reverse proxy (nginx, Cloudflare) IPs here.

💾 Your Backup Strategy — The Three-Layer Approach

If your VPS dies, how fast can you recover? Without a plan, the answer is: you can't. And that realisation usually comes right after something breaks.

Here's the framework I use across all my projects. It works for one VPS or ten, and you can set it up in an afternoon.

The Three-Layer Backup Principle:

  1. Layer 1 — On-VPS Backup: Your VPS creates backup files locally every day. The database gets dumped correctly (never just copied — more on that below). Old backups get pruned automatically.
  2. Layer 2 — Health Check: After every backup, a script verifies the backup file actually works. Corrupted backups are worse than no backups — they give you false confidence.
  3. Layer 3 — Off-Server Copy: The backup files get pulled to a completely different physical machine (in my case, the Mac Mini on my desk at home). If the VPS provider has an outage, your backups survive.

All three layers matter. Layer 1 without Layer 2 means you might be backing up garbage. Layers 1+2 without Layer 3 means a VPS-level disaster wipes everything including your backups.

🤖 AI — Set Up PostgreSQL Backup (pg_dump Only)

If your project uses PostgreSQL — and it should, don't use SQLite for anything real — never, ever copy the database files directly. PostgreSQL uses write-ahead logging and in-memory buffers. A cp of the data directory produces a corrupt backup more often than you'd think.

Always use pg_dump:

#!/bin/bash
# PostgreSQL backup with integrity check (for Your SaaS Project)
set -euo pipefail

INSTALL_DIR="/opt/realform"
BACKUP_DIR="$INSTALL_DIR/backups"
DB_URL=$(grep '^DB_URL=' "$INSTALL_DIR/.env" | cut -d= -f2-)
DATE=$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"

# Extract connection details from DATABASE_URL
# Format: postgresql://user:password@host:port/dbname
DB_NAME=$(echo "$DB_URL" | sed 's/.*\/\([^?]*\).*/\1/')

# Dump with custom format (compressed, parallel-restore capable)
pg_dump "$DB_URL" --format=custom --file="$BACKUP_DIR/db_${DATE}.dump"

# Verify the dump is valid
pg_restore --list "$BACKUP_DIR/db_${DATE}.dump" > /dev/null 2>&1
if [ $? -eq 0 ]; then
    echo "Integrity check passed"
else:
    # Send alert and abort
    echo "Backup integrity FAILED!" | mail -s "Backup FAILED" you@email.com
    exit 1
fi

# GFS retention (explained below)
echo "Backup complete: ${DATE}"

Key points: the --format=custom flag creates a compressed, flexible dump that you can restore selectively. The pg_restore --list check is your integrity verification — if it can list the contents, the dump is valid.

🤖 AI — Set Up SQLite Backup (.backup Command)

For smaller projects like Your Project that use SQLite (a valid choice for single-server apps), the principle is the same: never copy the file. SQLite has a built-in .backup command that handles concurrent reads safely:

#!/bin/bash
# SQLite backup with integrity check (for Your Project)
set -euo pipefail

INSTALL_DIR="/opt/your-project"
BACKUP_DIR="$INSTALL_DIR/backups"
DB_PATH="$INSTALL_DIR/instance/your-project.db"
DATE=$(date +%Y%m%d_%H%M%S)
DOW=$(date +%u)       # Day of week (1=Mon, 7=Sun)
DOM=$(date +%d)       # Day of month
LOG_FILE="/var/log/your-project/backup.log"

mkdir -p "$BACKUP_DIR" "$(dirname "$LOG_FILE")"

log() { echo "[$(date)] $*" | tee -a "$LOG_FILE"; }
fail() {
    log "FATAL: $*"
    # Send alert via SendGrid (see health check section below)
    /opt/your-project/scripts/send_alert.sh "Backup FAILED: $*"
    exit 1
}

log "Starting backup..."

# 1. Online-safe backup using .backup (NOT cp)
BACKUP_DB="$BACKUP_DIR/db_$DATE.sqlite"
if sqlite3 "$DB_PATH" ".backup '$BACKUP_DB'" 2>>"$LOG_FILE"; then
    log "SQLite backup created"
else
    fail "sqlite3 .backup failed"
fi

# 2. MUST verify integrity — always, no exceptions
INTEGRITY=$(sqlite3 "$BACKUP_DB" "PRAGMA integrity_check;" 2>&1)
if [ "$INTEGRITY" = "ok" ]; then
    log "Backup integrity: OK"
else
    fail "Backup integrity FAILED: $INTEGRITY"
fi

# 3. Back up config files (exclude .env with secrets)
tar -czf "$BACKUP_DIR/config_$DATE.tar.gz" \
    /etc/postfix/main.cf \
    /etc/postfix/master.cf \
    /etc/nginx/sites-available/your-project.net \
    2>/dev/null || log "WARNING: Config tar had errors"

# 4. GFS retention — prune old backups
log "Backup complete: $DATE"

The .backup command creates an ACID-safe snapshot even while the database is being written to. The PRAGMA integrity_check; after backup is non-negotiable — I've had corrupted backups that looked fine by file size but failed integrity. That check saved me.

🧑 Human — GFS Retention Explained

GFS stands for Grandfather-Father-Son. It's a backup rotation strategy that balances recovery flexibility with storage cost. Here's the pattern I use:

  • 14 daily backups: Keep the last 14 days. Good for "I deleted something yesterday" recovery.
  • 8 weekly backups: Every Sunday, a copy gets promoted to weekly storage. Covers about 2 months.
  • 12 monthly backups: On the 1st of each month, a copy goes to monthly storage. Covers a full year.

In the backup script, you implement it like this:

# GFS: Weekly copy (Sunday = day 7)
if [ "$DOW" = "7" ]; then
    cp "$BACKUP_DB" "$WEEKLY_DIR/db_$DATE.sqlite"
    # Keep only last 8 weekly backups
    ls -1t "$WEEKLY_DIR"/db_*.sqlite | tail -n +9 | xargs rm -f 2>/dev/null || true
fi

# GFS: Monthly copy (1st of month)
MONTH_TAG=$(date +%Y%m)
if [ "$DOM" = "01" ]; then
    cp "$BACKUP_DB" "$MONTHLY_DIR/db_${MONTH_TAG}.sqlite"
    # Keep only last 12 monthly backups
    ls -1t "$MONTHLY_DIR"/db_*.sqlite | tail -n +13 | xargs rm -f 2>/dev/null || true
fi

# Daily cleanup: delete backups older than 14 days
find "$BACKUP_DIR" -maxdepth 1 -type f -mtime +14 -delete

The sorting trick (ls -1t ... | tail -n +9 | xargs rm) keeps the newest N files and deletes the rest. It means you always have recent granularity and long-term coverage, without filling up your disk.

🩺 Health Check Scripts — Catch Problems Before They Catch You

A backup that sits unverified is a hope, not a plan. You need automated checks that run after every backup and email you if anything is wrong.

Here's the health check principle: never fail silently. If a backup fails, the health check sends an email. If a backup succeeds but integrity fails, it sends an email. If the VPS is unreachable, it sends an email. No news is good news — and that only works if you trust that bad news always arrives.

🤖 AI — Deploy the Backup Health Check Script

This Python script SSHes into your VPS, checks the latest backup, verifies its integrity, and emails you via SendGrid if anything's wrong:

#!/usr/bin/env python3
"""
Backup Health Check — run daily after backup completes.
SSHes to VPS, verifies latest dump, checks log.
Sends alert via SendGrid if anything is wrong.

Usage: python3 backup_health_check.py <sendgrid_api_key>
"""

import subprocess, sys, json, datetime, urllib.request
from typing import Optional, Tuple

VPS_HOST = "YOUR_VPS_IP"
VPS_USER = "root"
BACKUP_DIR = "/opt/yourproject/backups"
LOG_FILE  = "/var/log/yourproject/backup.log"
FROM_ADDR = "backup-monitor@yourproject.com"
TO_ADDR   = "you@email.com"
SENDGRID  = "https://api.sendgrid.com/v3/mail/send"
TODAY     = datetime.date.today().strftime("%Y-%m-%d")

def ssh(cmd: str) -> Tuple[int, str, str]:
    full_cmd = [
        "ssh", "-o", "ConnectTimeout=10",
        "-o", "StrictHostKeyChecking=accept-new",
        f"{VPS_USER}@{VPS_HOST}", cmd
    ]
    r = subprocess.run(full_cmd, capture_output=True, text=True, timeout=30)
    return r.returncode, r.stdout.strip(), r.stderr.strip()

def send_alert(sg_key: str, subject: str, body: str):
    payload = json.dumps({
        "personalizations": [{"to": [{"email": TO_ADDR}], "subject": subject}],
        "from": {"email": FROM_ADDR, "name": "Backup Monitor"},
        "content": [{"type": "text/plain", "value": body}],
    }).encode()
    req = urllib.request.Request(SENDGRID, data=payload, method="POST")
    req.add_header("Content-Type", "application/json")
    req.add_header("Authorization", f"Bearer {sg_key}")
    urllib.request.urlopen(req, timeout=15)

# 1. Check VPS is reachable
code, out, err = ssh("echo ok")
if code != 0:
    send_alert(sg_key, "ALERT: VPS UNREACHABLE",
               f"Cannot SSH to {VPS_HOST}\n{err}")
    sys.exit(1)

# 2. Check latest dump exists and has size
cmd = f"""
LATEST=$(ls -t {BACKUP_DIR}/db_*.sqlite 2>/dev/null | head -1)
[ -n "$LATEST" ] || {{ echo "ERROR: No backup files"; exit 1; }}
SIZE=$(stat -c%s "$LATEST" 2>/dev/null || stat -f%z "$LATEST" 2>/dev/null)
[ "$SIZE" -gt 0 ] || {{ echo "ERROR: Zero-byte backup"; exit 1; }}
echo "FILE:$LATEST SIZE:$SIZE"
"""
code, out, err = ssh(cmd)
if code != 0:
    send_alert(sg_key, "ALERT: Backup Missing or Empty", out or err)
    sys.exit(1)

# 3. Check backup integrity
latest_path = out.split("FILE:")[1].split(" ")[0]
code, out, _ = ssh(f"sqlite3 {latest_path} 'PRAGMA integrity_check;'")
if "ok" not in out.lower():
    send_alert(sg_key, "ALERT: Backup Integrity FAILED",
               f"Integrity check failed on {latest_path}\n{out}")
    sys.exit(1)

# 4. Check backup log for errors
code, out, _ = ssh(f"grep '{TODAY}.*FATAL' {LOG_FILE} || echo none")
if out and out != "none":
    send_alert(sg_key, "ALERT: Backup Log Shows Errors", out)
    sys.exit(1)

print(f"All checks passed for {TODAY}")

Run this script every day, right after the backup completes. If you use cron, stagger them: backup at 3am, health check at 3:30am.

🧑 Human — What About a Full Daily Health Check?

Beyond just backup verification, you'll want a broader health check that runs once a day and checks everything: services, disk space, SSL certificates, application endpoints. Here's the one I run every morning at 9am AEST:

#!/usr/bin/env python3
"""
Daily Health Check — runs every morning, emails only on failure.
Checks: HTTP endpoints, service status, disk usage, SSL expiry, backup age.
"""
import subprocess, os, sys
from datetime import datetime, timezone

AEST = datetime.now(timezone.utc).astimezone()
ISSUES = []

def check_http(name, url):
    r = subprocess.run(
        ["curl", "-sI", "-o", "/dev/null", "-w", "%{http_code}",
         "--max-time", "10", url],
        capture_output=True, text=True, timeout=15
    )
    if r.stdout.strip() != "200":
        ISSUES.append(f"{name}: HTTP {r.stdout.strip()}")

def check_vps(host, name, services):
    for svc in services:
        out = subprocess.run(
            ["ssh", host, f"systemctl is-active {svc}"],
            capture_output=True, text=True, timeout=10
        )
        if out.stdout.strip() != "active":
            ISSUES.append(f"{name}: {svc} is {out.stdout.strip()}")

    # Disk
    out = subprocess.run(
        ["ssh", host, "df -h / | tail -1 | awk '{print $5}'"],
        capture_output=True, text=True, timeout=10
    )
    pct = int(out.stdout.strip().rstrip('%'))
    if pct >= 85:
        ISSUES.append(f"{name}: Disk at {out.stdout.strip()}")

    # Backup age
    out = subprocess.run(
        ["ssh", host,
         "ls -t /opt/yourproject/backups/db_*.sqlite | head -1 "
         "| xargs basename | sed 's/db_//;s/\\.sqlite//'"],
        capture_output=True, text=True, timeout=10
    )
    try:
        bkup = datetime.strptime(out.stdout.strip(), "%Y%m%d_%H%M%S")
        hours = (datetime.now() - bkup).total_seconds() / 3600
        if hours > 27:
            ISSUES.append(f"{name}: Backup {hours:.0f}h old")
    except:
        pass

# Check each project
check_http("Your Project", "https://your-project.net")
check_http("Straya Co", "https://strayaco.com.au")
check_vps("root@YOUR_SECOND_VPS_IP", "Your Project VPS",
          ["your-project", "nginx", "postfix"])

if ISSUES:
    body = f"Daily Health Check — {len(ISSUES)} issues\n\n"
    for i, issue in enumerate(ISSUES, 1):
        body += f"{i}. {issue}\n"
    # Send via SendGrid or local mail
    send_alert("you@example.com.au",
               f"[Health Check] {len(ISSUES)} issue(s)",
               body)

The beauty of email-on-failure-only is that you don't get desensitised. No "Everything OK" email to ignore every morning. If the inbox stays quiet, everything is fine.

📤 Off-Server Backup Pull — Your Insurance Policy

Your VPS provider could go bankrupt tomorrow. Their data centre could flood. Your account could get hacked and wiped. If your only backup lives on the VPS, you lose everything with it.

The fix is simple: pull backups to a completely different machine on a different network. For me, that's the Mac Mini in my home office pulling from the VPS in Sydney.

This has saved me. Multiple times. When my VPS provider had a billing glitch and suspended servers, I had clean copies of everything on my local machine within minutes. No panic, no begging support, no data loss.

🤖 AI — Set Up Off-Server Backup Pull

#!/bin/bash
# Off-server backup pull — runs daily on your local machine
# Pulls backups from VPS, keeps 14 days locally.
set -euo pipefail

VPS="root@YOUR_SECOND_VPS_IP"
VPS_BACKUP_DIR="/opt/your-project/backups"
LOCAL_BACKUP_DIR="/Users/you/Your Project-Net/backups"
LOG_FILE="$LOCAL_BACKUP_DIR/pull.log"

mkdir -p "$LOCAL_BACKUP_DIR"

log() { echo "[$(date)] $*" | tee -a "$LOG_FILE"; }

log "Starting pull from VPS..."

# Pull new/changed files only (--ignore-existing skips duplicates)
rsync -avz --ignore-existing \
    -e "ssh -o ConnectTimeout=10" \
    "$VPS:$VPS_BACKUP_DIR/" "$LOCAL_BACKUP_DIR/" 2>&1 | tee -a "$LOG_FILE"

# Also pull the live database and configs directly
rsync -avz \
    "$VPS:/opt/your-project/.env" \
    "$LOCAL_BACKUP_DIR/.env" 2>&1

rsync -avz \
    "$VPS:/etc/postfix/main.cf" \
    "$VPS:/etc/nginx/sites-available/your-project.net" \
    "$LOCAL_BACKUP_DIR/" 2>&1

# Prune local backups older than 14 days
DELETED=$(find "$LOCAL_BACKUP_DIR" -type f -not -name "pull.log" \
          -mtime +14 -delete -print | wc -l)
log "Pruned $DELETED old local backup files"

log "Pull complete"
ls -lht "$LOCAL_BACKUP_DIR"/*.sqlite 2>/dev/null | head -6 | tee -a "$LOG_FILE"

The --ignore-existing flag means you only pull files you don't already have. Combined with 14-day retention on both sides, you build a 14-day window of overlapping backup history. Any backup that existed on the VPS for at least 24 hours also exists on your local machine.

🧪 Restore Testing — The Most Important Thing You Never Do

I'll say this plainly: a backup you haven't tested restoring is a prayer, not a plan. You need to verify your restore process works end-to-end, and you need to do it before an emergency.

Here's the restore procedure for a PostgreSQL project, step by step:

#!/bin/bash
# Restore from PostgreSQL backup
# Usage: ./restore.sh 20260509_040225
set -euo pipefail

BACKUP_DIR="/Users/you/Your SaaS Project/backups"
VPS="root@YOUR_VPS_IP"
INSTALL_DIR="/opt/realform"
DATE="${1}"

DB_BACKUP="$BACKUP_DIR/db_${DATE}.dump"

# Step 1: Verify the backup file is valid FIRST
pg_restore --list "$DB_BACKUP" > /dev/null 2>&1
if [ $? -ne 0 ]; then
    echo "ERROR: Backup file is corrupt — aborting"
    exit 1
fi

# Step 2: Stop the service
echo "Stopping service..."
ssh "$VPS" "systemctl stop realform"

# Step 3: Drop and recreate database
echo "Restoring database..."
scp "$DB_BACKUP" "$VPS:/tmp/restore.dump"
ssh "$VPS" "
    # Kill existing connections
    psql -U youruser -d postgres \\
        -c \"SELECT pg_terminate_backend(pid) FROM pg_stat_activity \\
             WHERE datname = 'yourdb' AND pid <> pg_backend_pid();\"
    dropdb --if-exists yourdb
    createdb yourdb
    pg_restore -d yourdb /tmp/restore.dump
    rm /tmp/restore.dump
"

# Step 4: Start the service
ssh "$VPS" "systemctl start realform"
sleep 2

# Step 5: Verify
ssh "$VPS" "systemctl is-active realform" | grep -q active
echo "Restore complete — service is running"

Schedule a quarterly restore drill. Pick a backup from two months ago, restore it to a test environment, and verify the application works with the restored data. Document the process. Time yourself. If it takes longer than 30 minutes, optimise until it does.

When real disaster hits — and it will eventually — you'll be grateful you practised.

🔄 PostgreSQL WAL Archiving

If you're running PostgreSQL in production and your backup window matters, you need WAL archiving on top of your daily pg_dump.

WAL (Write-Ahead Log) archiving gives you point-in-time recovery (PITR). Instead of restoring to the last backup, you can restore to any moment — 3:47 pm Tuesday, for example. This is critical if corruption happens mid-day and you don't want to lose 12 hours of data.

In postgresql.conf:

wal_level = replica
archive_mode = on
archive_command = 'test ! -f /var/lib/postgresql/14/main/wal_archive/%f && cp %p /var/lib/postgresql/14/main/wal_archive/%f'
archive_timeout = 60          # Archive every 60 seconds at most

Then in your backup script, take a base backup and include WAL files:

# Full base backup with WAL archiving
pg_basebackup -D /backups/base_$(date +%Y%m%d) -X stream -z -P

# Or: pg_dump (simpler, no PITR) + separate WAL archive copy
pg_dump --format=custom --file="/backups/db_$(date +%Y%m%d_%H%M%S).dump"
rsync -avz /var/lib/postgresql/14/main/wal_archive/ /backups/wal/

Restoring from WAL involves replaying the archive to the exact second you want:

# In recovery.conf (PostgreSQL 12+) or postgresql.conf:
restore_command = 'cp /var/lib/postgresql/14/main/wal_archive/%f %p'
recovery_target_time = '2026-05-20 15:47:00 AEST'

For most small-to-medium projects, daily pg_dump is sufficient. Add WAL archiving when data loss of even a few hours is unacceptable.

SPF, DKIM, and DMARC — The DNS Records

; SPF — who's allowed to send as your domain
; Use -all (hard fail), NEVER ~all (soft fail)
yourdomain.com.  IN  TXT  "v=spf1 ip4:YOUR_VPS_IP include:sendgrid.net -all"

; DKIM — SendGrid provides this after domain verification
sg._domainkey.yourdomain.com.  IN  TXT  "k=rsa; t=s; p=MIGfMA0GCSq..."

; DMARC — what to do when SPF and DKIM both fail
_dmarc.yourdomain.com.  IN  TXT  "v=DMARC1; p=reject; rua=mailto:dmarc@yourdomain.com"

Why -all not ~all: Soft fail (~all) means "this might be spam, but deliver it anyway." We learned this the hard way — a French spammer spoofed our domain and the email still landed in the inbox because SPF was set to soft fail. Switching to hard fail (-all) blocks spoofed emails outright.

Every API call returns 401. Resolve all secrets to their actual values before they touch .env. This caused 7 hours of outage and is the #1 trap for OpenClaw on macOS.
18Never use openclaw gateway install --force as a post-update fixinstall --force uses a destructive bootout→bootstrap pattern. If bootstrap fails (and it often does after major updates), your LaunchAgent is orphaned — KeepAlive can't recover it, and the gateway stays dead. Use openclaw doctor --yes instead. It uses enable→bootstrap+kickstart, the non-destructive fallback that actually works. This bug killed our gateway for 7 hours.
19Self-improvement loop: update lessons after every correctionEvery mistake you fix today is a lesson for tomorrow — if you write it down. Without it, the same mistake repeats.

🧑 Human — Closing Note

Start with Agentmail.to — it's free, instant, and perfect for a personal AI agent. You can always add SendGrid later when you have a custom domain and need branded transactional email.

Email is the one part of your AI stack that can break silently for days before you notice. The health check scripts in Section 4 catch most failures, but nothing replaces actually sending a test email and checking your inbox once a week. Do it.
