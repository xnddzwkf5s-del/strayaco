1. The Problem: Why AI Agents Need Memory

AI agents are fundamentally stateless. Every session starts from a clean slate. The context window is a blank page—and it stays that way because the architecture gives no affordance for persistence between invocations.

This creates four problems that compound over time:

Same mistakes, every time. An agent discovers that a particular nginx configuration breaks certain static pages. It documents this, fixes the issue, and moves on. Next session? The lesson is gone. The same four-hour debugging loop repeats.

Context windows are limited. Even with 200K+ token windows, you can't pack every past lesson into every prompt. The economics of token usage degrade as you shove more history into each call. You need selectivity—load only what's relevant to this task.

Knowledge silos between agents. In our setup, Conductor (a reviewer/gatekeeper/architect on a Mac mini) and Worker (a coding agent on a remote VPS) each learn different lessons from different contexts. Without a shared mechanism, Worker's hard-won deploy lessons never reach Conductor. Conductor's architectural directives never constrain Worker.

No forced forgetting. A human developer naturally forgets obsolete patterns. An AI agent with infinite memory accumulates rules forever—including rules that are no longer relevant, rules that contradict newer ones, and rules from codebases that have been rewritten. Without expiry, the rule base becomes noise.

Recursive learning is our answer to all four problems. It's a tiered, self-expiring, contradiction-aware system that captures lessons from each session and feeds them back into the next—creating a closed loop of continuous improvement. It runs on zero additional infrastructure—just JSONL files, SSH, and three Python scripts.

2. Design Principles

We made deliberate architectural choices. Here's each one, with its rationale.

File-Based Over Database

A PostgreSQL-backed rule store would be elegant. It would also be another service to monitor, another connection string to manage, and another failure mode. Our agents already have working filesystems. JSONL files are trivially inspectable with cat and grep, infinitely portable, and require zero setup. For a rule base of hundreds (not millions) of entries, the filesystem is the perfect database.

SSH-Mediated Over GitHub

Worker has no direct access to the Mac mini. All cross-agent communication flows one direction: Mac mini → Worker via SSH push. This is intentional—the Mac mini is the gatekeeper, and Worker is the worker. Conductor pushes critical rules to Worker, and pulls Worker's learned rules back for review. No shared infrastructure, no central server, no authentication tokens to leak. Just SSH keys with restricted command= directives.

JSONL Over YAML

YAML is readable but dangerous: anchors, aliases, and the Norway problem (no → false) make it a poor serialisation format for machine-written data. JSONL (one JSON object per line) is concurrent-append-safe—multiple writers can append lines without corrupting each other's data. There's no parser ambiguity, no RCE vector (Python's yaml.load), and no split-brain risk. Each line is self-validating.

Tiered Knowledge

Not all rules are equal. Some are always relevant (critical rules: "never deploy without verifying permissions"). Some are project-specific (WeScan deployment rules shouldn't load for a Realform session). Some are niche and rarely needed. We use three tiers:

TierFileWhen Loaded
Criticalcritical.jsonlAlways, for matching scope
Directivesdirectives.jsonlAlways, filterable by scope
Learnedlearned.jsonlFiltered by scope, capped at 50

Forced Forgetting

Every rule has a 90-day expiry. A rule that never triggers in 90 days almost certainly isn't useful. Rules that do trigger get auto-renewed—the system rewards relevance. Stale rules (60+ days since last triggered) are downgraded and eventually archived. This prevents rule bloat without any human intervention.

Degradation-First Philosophy

The system must never block actual work. If a JSONL file is missing, corrupt, or unreadable—continue with zero rules. If SSH to the remote agent fails—continue with local rules only. If a line can't be parsed as JSON—skip it and log a warning. The agent always proceeds. Rules are an enhancement, not a prerequisite.

Bankruptcy Protection

A buggy session could theoretically flood the rule base with hundreds of low-quality entries. We cap at 10 new rules per session. Exceed that, and the system enters lockdown—all new rules are rejected, and an alert fires. This isn't just about storage; it's about maintaining signal-to-noise ratio in the rule base.

Contradiction Kill Switch

What happens when one rule says "always do X" and another says "never do X"? Both get archived. Immediately. The contradiction is flagged for human review. The system refuses to pick sides—that's for a human to resolve.

Data flow is unidirectional for writes. Conductor pushes rules to Worker. Worker writes locally and Conductor pulls. Worker never initiates connections to the Mac mini. This simplifies firewall rules and reduces the attack surface.

Two Agents, Two Roles

Conductor (Mac mini) is the reviewer and gatekeeper. It reads Worker's learned rules during daily health checks, promotes valuable rules to critical, detects contradiction patterns, sends email alerts, and runs the automated review cadence (weekly & monthly). It also writes directives that encode architectural decisions.

Worker (VPS) is the coding agent. At session startup, it loads all three rule files, filters by project context, detects contradictions, and enforces the 50-rule cap. During the session, it consults loaded rules before making decisions. At session end, it reflects on what was learned and writes new rules via write_rule.py.

4. Two-Layer Self-Improvement System

The v4 JSONL rule system was a solid start—it gave us machine-actionable rules that loaded at session startup. But it had a blind spot: context. A JSONL entry can encode a rule and a rationale, but it can't tell the story of how that rule was discovered, why it matters, and what mistakes preceded it. That's where the two-layer design comes in.

The Two Layers

LayerFilePurposeFormat
Narrativetasks/lessons.mdFull-context: Mistake → Root Cause → Rule. Human-readable, dated. Tells the story of each lesson.Markdown with structured sections
Structured.learnings/LEARNINGS.mdMachine-actionable: IDs, recurrence tracking, status workflow, cross-references. What the agent reads at startup.Markdown tables
Structured.learnings/ERRORS.mdAuto-logged command failures. Captured immediately when an exec command exits non-zero.Markdown with error details
Structured.learnings/FEATURE_REQUESTS.mdUser-requested capabilities that need tracking.Markdown with priority and status

Why Both Layers Exist

The narrative layer is for the human. When Vincent wants to understand why a particular rule exists—what mistake led to it, what the root cause was, and what alternative approaches were considered—he reads lessons.md. Each entry is a mini post-mortem with enough context to evaluate the decision.

The structured layer is for the agent. It's what gets checked at session startup (see AGENTS.md step 3b). It's optimised for grep, for parsing, and for automated promotion decisions. No narrative fluff—just IDs, statuses, recurrence counts, and cross-references.

Cross-Referencing

The two layers are linked so you can navigate between them:

  • Each lessons.md entry carries a Learnings-Ref field pointing to its structured counterpart: Learnings-Ref: LRN-YYYYMMDD-XXX
  • Each structured entry carries a Lessons-Ref field: Lessons-Ref: LESSON-YYYYMMDD-XXX

This lets you start from a dense table in LEARNINGS.md, follow the link to a detailed narrative, and understand the full context. Or start from a post-mortem in lessons.md and see where it landed in the structured system.

Auto-Error-Detection

One of the most practical features: after ANY exec command that exits non-zero or shows error output (Permission denied, failed, crash, 404, etc.), the agent is instructed to log it to .learnings/ERRORS.md immediately—not waiting for human correction. This catches issues at the moment they happen, when the context is freshest, rather than during a post-session review hours later.

Why auto-detection matters: Before this feature, errors that didn't block the current task were silently forgotten. A flaky SSH connection that succeeded on retry, a permissions warning that got papered over—these accumulated into reliability debt. Now every non-zero exit is captured with enough context (command, error output, timestamp) to diagnose patterns.

AGENTS.md Startup Integration

The structured learning files aren't optional reading—they're wired directly into the agent startup sequence. Step 3b of AGENTS.md instructs the agent to check .learnings/ items at the start of every session, specifically to:

  • Review high-priority items first
  • Check for recurrence warnings (count ≥ 2)
  • Identify items ready for promotion

This ensures the learning system isn't a passive archive—it actively shapes what the agent pays attention to in each new session.

5. Rule & Learning Formats

5.1 JSONL Rules (Worker/Conductor)

Every rule is a single JSON object on one line.

{
  "id": "WRKR-001",
  "version": 1,
  "rule": "Always check nginx location blocks before creating static pages",
  "rationale": "Creating /login.html when nginx proxies /login causes 404",
  "category": "infrastructure",
  "scope": ["wescan", "realform"],
  "source": "worker",
  "priority": "critical",
  "maturity": "active",
  "created": "2026-05-23T00:00:00Z",
  "last_triggered": null,
  "trigger_count": 0,
  "expires": "2026-08-21T00:00:00Z",
  "refs": ["WRKR-005"],
  "contradicts": null
}
FieldPurpose
idUnique identifier. WRKR-NNN for Worker-written rules, CONDUCTOR-NNN for Conductor directives.
versionStarts at 1, incremented on updates. Allows tracking rule evolution.
ruleThe actionable one-sentence rule. Max 200 characters.
rationaleWhy this rule exists—the mistake it prevents. Max 500 characters.
categoryClassification: infrastructure, security, deploy, code, nginx, etc.
scopeWhich projects this applies to: wescan, realform, strayaco, openclaw, general.
prioritycritical (always loaded), high, normal, low. Drives cap-enforcement ordering.
maturityLifecycle stage: captured → tested → active → stale → archived.
trigger_countHow many times this rule was consulted. Drives promotion.
expiresISO-8601, created + 90 days. Auto-renewed if trigger_count > 0.
contradictsArray of rule IDs this rule conflicts with. Mutual archive trigger.

5.2 Structured Learning Format (.learnings/)

Each structured entry follows a consistent format across all .learnings/ files:

Categoryinfrastructure, security, deploy, code, process, config, etc.

5.3 Narrative Format (lessons.md)

The narrative layer uses a richer format with full context:

## LESSON-20260523-001 — Always use UTC-aware datetime comparisons

**Date:** 2026-05-23 | **Project:** wescan | **Category:** infrastructure | **Learnings-Ref:** LRN-20260523-001

**Mistake:** Backup health check compared file modification timestamps against calendar days, causing false failures for backups that ran just after midnight UTC.

**Root Cause:** Used datetime.date comparisons instead of timezone-aware UTC comparisons. The issue only manifested during a small window after midnight, making it hard to reproduce.

**Resolution:** Changed all backup timestamp comparisons to use aware UTC datetimes.

**Rule:** Always use timezone-aware UTC datetime comparisons for any health check or alerting logic. Never use naive dates.

**Prevention:** Added a critical JSONL rule; loaded at every session startup.

6. Lifecycle, Recurrence Tracking & Review Cadence

6.1 JSONL Rule Lifecycle

captured ──→ tested ──→ active ──→ stale (60d) ──→ archived (90d)
               │                                        ↑
               └──→ promoted ──→ critical.jsonl         │
                                                        │
                    contradiction detected ──────────────┘
                    (mutual archive within same scope)
StageConditionAction
capturedNewly written, never triggeredDefault for new rules. Loaded at low priority.
testedTriggered at least onceAuto-promoted by loader. Rule has been useful.
activeTriggered 3+ times within expiry windowStable, proven rule. High confidence.
promotedTriggered 5+ timesMoved to critical.jsonl by Conductor review.
stalelast_triggered > 60 days agoWon't load automatically.
archivedExpired, or stale > 90 days, or contradictedNot loaded. Audit trail only.

6.2 Structured Entry Status Workflow

The structured entries in .learnings/ follow their own lifecycle mirroring the rule lifecycle:

pending ──→ in_progress ──→ resolved ──→ promoted ──→ wont_fix
                               ↑                            │
                               └────────────────────────────┘
                                   (recurrence reopens)
StatusMeaning
pendingIdentified but not yet acted upon. Freshly logged.
in_progressActively being worked on or rule being drafted.
resolvedRule written and deployed. Pattern addressed.
promotedRule promoted to permanent context (AGENTS.md, SOUL.md, TOOLS.md). Highest confidence.
wont_fixAssessed and deemed not worth encoding. Closed permanently.

A resolved entry can be reopened (set back to pending) if the pattern recurs—the system never permanently closes topics that keep coming back.

6.3 Recurrence Tracking & Auto-Promotion

This is the heart of the self-improvement system. Every structured entry tracks:

  • Recurrence-Count: How many times this pattern has been observed. Starts at 1, incremented each time the same mistake or insight reoccurs.
  • First-Seen: When the pattern was first logged.
  • Last-Seen: Updated every time the pattern recurs.

Promotion threshold: When Recurrence-Count ≥ 3 across 2+ distinct tasks within 30 days, the pattern auto-promotes. At that point:

  1. The entry's status moves to promoted
  2. The rule is permanently embedded into the agent's context files (AGENTS.md, SOUL.md, or TOOLS.md)
  3. The pattern ceases to be a "learning" and becomes part of the agent's identity

This is how transient lessons become permanent behaviour. The system doesn't blindly elevate everything—it waits for evidence that a pattern is genuinely recurring before committing it to long-term memory.

6.4 Automated Review Cadence

The review process is fully automated via OpenClaw cron, running in an isolated sub-agent session:

CadenceWhenActions
WeeklyMonday 09:00Scan open items by priority; check recurrence warnings (count ≥ 2); promote RC ≥ 3 patterns to permanent context
Monthly1st of month 09:00Close stale pending items (60+ days no update → wont_fix); consolidate duplicate Pattern-Keys; review promotions this month

Each review runs in a fresh sub-agent session with a dedicated spec. The sub-agent reads the structured files, applies the rules above, makes changes, and reports back. Conductor reviews the report and approves or rolls back.

This ensures the learning system never goes unmaintained. Without scheduled review, the structured files accumulate noise and the promotion mechanism stalls. The cadence is the heartbeat of the system.

7. Core Implementation

Three Python scripts form the engine. Together they're under 250 lines. Here's each one, annotated.

7.1 load_rules.py — Session Startup Loader

Runs at the start of every Worker session. Must be fast (<500ms). Reads all three rule files, filters by scope, detects contradictions, enforces the 50-rule cap, and outputs the loaded rule set.

#!/usr/bin/env python3
"""T-Learning: Rule loader for Worker."""
import json, os, sys
from datetime import datetime, timezone, timedelta
RULES_DIR = "/opt/openclaw/workspace/rules"
MAX_RULES = 50
PRIORITY_ORDER = {"critical": 0, "high": 1, "normal": 2, "low": 3}
def load_jsonl(path: str) -> list:
    rules = []
    if not os.path.exists(path):
        print(f"[Rules] File not found: {path}")
        return rules
    with open(path) as f:
        for i, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                rules.append(json.loads(line))
            except json.JSONDecodeError:
                print(f"[Rules] WARNING: Corrupt line {i} in {path}, skipping")
    return rules
def check_age(rule: dict) -> dict:
    now = datetime.now(timezone.utc)
    try:
        expires = datetime.fromisoformat(rule["expires"])
        if now > expires:
            if rule.get("trigger_count", 0) == 0:
                rule["maturity"] = "archived"
            else:
                rule["expires"] = (now + timedelta(days=90)).isoformat()
                rule["maturity"] = "active"
    except (ValueError, KeyError):
        pass
    if rule["maturity"] == "active" and rule.get("last_triggered"):
        try:
            last = datetime.fromisoformat(rule["last_triggered"])
            days_since = (now - last).days
            if days_since > 60:
                rule["maturity"] = "stale"
            if days_since > 90:
                rule["maturity"] = "archived"
        except (ValueError, KeyError):
            pass
    return rule
def has_contradiction(a: dict, b: dict) -> bool:
    if a.get("contradicts") and b["id"] in a["contradicts"]:
        return True
    if b.get("contradicts") and a["id"] in b["contradicts"]:
        return True
    return False
def load_rules(session_scopes: list) -> list:
    all_rules = (load_jsonl(os.path.join(RULES_DIR, "critical.jsonl")) +
                 load_jsonl(os.path.join(RULES_DIR, "directives.jsonl")) +
                 load_jsonl(os.path.join(RULES_DIR, "learned.jsonl")))
    all_rules = [check_age(r) for r in all_rules]
    scoped = [r for r in all_rules
              if set(r.get("scope", ["general"])) & set(session_scopes)]
    active = []
    for r in scoped:
        if r["maturity"] in ("archived", "stale"):
            continue
        for a in active:
            if has_contradiction(a, r):
                a["maturity"] = "archived"
                r["maturity"] = "archived"
                print(f"[Rules] Contradiction: {a['id']} vs {r['id']}")
                break
        else:
            active.append(r)
    active.sort(key=lambda r: (
        PRIORITY_ORDER.get(r.get("priority", "normal"), 99),
        -r.get("trigger_count", 0),
        r.get("created", "")))
    return active[:MAX_RULES]

Key details: load_jsonl() skips corrupt lines—a partially-written line from a crash won't block startup. check_age() auto-renews active rules. Contradiction detection uses the contradicts field. The sort key prioritises critical rules, then high-trigger-count rules, then newest.

7.2 write_rule.py — Post-Session Writer

Called at the end of a session when Worker identifies a new lesson. Validates, deduplicates, checks for contradictions, enforces bankruptcy limits, and performs an atomic append.

#!/usr/bin/env python3
"""T-Learning: Rule writer for Worker."""
import json, os, sys
from datetime import datetime, timezone, timedelta
from difflib import SequenceMatcher
RULES_DIR = "/opt/openclaw/workspace/rules"
BANKRUPTCY_LIMIT = 10
def similarity(a: str, b: str) -> float:
    return SequenceMatcher(None, a.lower(), b.lower()).ratio()
def get_next_id(rules: list, prefix: str = "WRKR") -> str:
    max_num = 0
    for r in rules:
        rid = r.get("id", "")
        if rid.startswith(prefix):
            try:
                max_num = max(max_num, int(rid.split("-")[1]))
            except (IndexError, ValueError):
                pass
    return f"{prefix}-{max_num + 1:03d}"
def check_bankruptcy() -> bool:
    learned = load_jsonl(os.path.join(RULES_DIR, "learned.jsonl"))
    session_start = os.environ.get("WRKR_SESSION_START")
    if not session_start:
        return False
    try:
        start = datetime.fromisoformat(session_start)
        recent = [r for r in learned
                  if datetime.fromisoformat(r.get("created", "1970")) > start]
        return len(recent) >= BANKRUPTCY_LIMIT
    except (ValueError, KeyError):
        return False
def write_rule(rule_data: dict) -> dict:
    if check_bankruptcy():
        return {"id": None, "status": "bankrupted"}
    for field in ["rule", "category", "scope", "priority", "source"]:
        if field not in rule_data:
            return {"id": None, "status": "invalid", "message": f"Missing: {field}"}
    all_rules = (load_jsonl(os.path.join(RULES_DIR, "learned.jsonl")) +
                 load_jsonl(os.path.join(RULES_DIR, "directives.jsonl")) +
                 load_jsonl(os.path.join(RULES_DIR, "critical.jsonl")))
    for r in all_rules:
        if similarity(r["rule"], rule_data["rule"]) > 0.8:
            return {"id": r["id"], "status": "duplicate"}
    now = datetime.now(timezone.utc)
    rule_data.setdefault("version", 1)
    rule_data.setdefault("maturity", "captured")
    rule_data.setdefault("trigger_count", 0)
    rule_data.setdefault("refs", [])
    rule_data["id"] = get_next_id(all_rules, "WRKR")
    rule_data["created"] = now.isoformat()
    rule_data["expires"] = (now + timedelta(days=90)).isoformat()
    new_line = json.dumps(rule_data, sort_keys=True) + "\n"
    temp = os.path.join(RULES_DIR, "learned.jsonl.tmp")
    real = os.path.join(RULES_DIR, "learned.jsonl")
    with open(temp, "w") as f:
        f.write(new_line)
    if os.path.exists(real):
        with open(real) as old, open(temp, "a") as new:
            new.write(old.read())
    os.rename(temp, real)
    return {"id": rule_data["id"], "status": "written"}

Key details: Atomic append via temp file + os.rename(). Dedup uses SequenceMatcher at 80% similarity threshold. Bankruptcy check uses WRKR_SESSION_START environment variable.

7.3 rules_alert.py — Alert Queue Writer

Standalone script for writing alert files.

#!/usr/bin/env python3
"""T-Learning: Alert queue writer."""
import json, os, sys
from datetime import datetime, timezone
ALERT_DIR = "/opt/openclaw/workspace/rules/alerts/pending"
def write_alert(alert_type: str, message: str, severity: str = "P1"):
    os.makedirs(ALERT_DIR, exist_ok=True)
    alert = {
        "type": alert_type, "message": message, "severity": severity,
        "timestamp": datetime.now(timezone.utc).isoformat()}
    path = os.path.join(ALERT_DIR, f"{alert_type}-{int(datetime.now().timestamp())}.json")
    with open(path, "w") as f:
        json.dump(alert, f)
if __name__ == "__main__":
    if len(sys.argv) < 3:
        print("Usage: rules_alert.py   [severity]")
        sys.exit(1)
    write_alert(sys.argv[1], sys.argv[2], sys.argv[3] if len(sys.argv) > 3 else "P1")

Key details: Alerts are individual JSON files in alerts/pending/. Conductor's daily cron scans this directory, sends alerts via email, and moves files to alerts/sent/. No network calls from Worker.

8. Fail-Safes & Loop Prevention

Self-modifying systems are dangerous. Without safeguards, they loop, bloat, or oscillate. We built five independent mechanisms that interlock.

8.1 Forced Forgetting (Expiry)

Every rule expires 90 days after creation. Rules that have triggered at least once get auto-renewed for another 90 days. Rules that never triggered are archived. Rules that went 60+ days without triggering are marked stale and eventually archived. This is self-tuning—useful rules stay, noise fades.

8.2 Bankruptcy Protection

If Worker writes more than 10 rules in a single session, the system enters lockdown. All subsequent writes are rejected. An alert fires. This prevents a single buggy session from polluting the entire rule base.

Recovery from bankruptcy: Conductor reviews the rejected rules and decides which (if any) to manually promote. The bankruptcy flag is session-scoped—it clears automatically on next session start.

8.3 Contradiction Kill Switch

When load_rules.py detects two rules with overlapping scope that explicitly reference each other in their contradicts fields, both are archived immediately. Neither is loaded. An alert goes to the human. The system does not attempt to resolve the contradiction—it defers to human judgment.

8.4 Repeat Mistake Escalation

Conductor's daily health check scans session logs. If it detects the same mistake pattern more than three times in 30 days—despite active rules meant to prevent it—the system escalates. New rule writing is deferred. Conductor emails the human with a specific recommendation.

8.5 Degradation (Never Blocking)

This is the most important fail-safe. Under no circumstance does the rule system prevent productive work:

FailureBehaviour
Rule file missingContinue with 0 rules
SSH to remote agent failsContinue with local rules only
Corrupt JSON line in fileSkip line, log warning, continue
All three files missingContinue with empty ruleset
Write failure (disk full)Log error, continue session without writing
Bankruptcy triggeredReject new writes, continue session with loaded rules

The agent always proceeds. Rules are an enhancement layer, not a dependency.

9. Comparison: pskoett vs Our Approach

The pskoett/self-improving-agent project on ClawHub was a significant influence on our architecture. It pioneered the idea of structured self-improvement for OpenClaw agents. But we diverged in several important ways.

What We Adopted

FeatureSourceOur Implementation
Structured IDspskoett's TASK-NNN formatLRN/ERR/FEAT-YYYYMMDD-NNN with date prefix for sortability
Recurrence trackingpskoett's repeat detectionRecurrence-Count with First-Seen / Last-Seen timestamps
Status workflowpskoett's state machineExtended to 5 states: pending → in_progress → resolved → promoted → wont_fix
Promotion targetspskoett's "commit to config"Promote to AGENTS.md, SOUL.md, or TOOLS.md with auto-merge verification

What We Did Differently

Narrative layer (our addition). pskoett's system is purely structured—tables of rules with no context. Without a narrative layer, reviewing and debugging the learning system was painful. The narrative layer fills this gap with full Mistake → Root Cause → Rule post-mortems, cross-referenced back to the structured entry.

Cross-referencing (our addition). pskoett's system doesn't link between structured and narrative formats. We added bidirectional cross-references (Lessons-Ref / Learnings-Ref) so you can navigate seamlessly between the dense table and the detailed story.

Automated review cadence (our addition). pskoett's system relies on manual review. We automate the review process with weekly and monthly cadences run via OpenClaw cron. The system doesn't just accumulate rules—it actively grooms them, closes stale entries, and promotes recurrent patterns.

AGENTS.md startup integration (our addition). In pskoett's system, the agent must explicitly check learning files—it's a convention, not a requirement. We wired .learnings/ checking directly into the AGENTS.md startup sequence (step 3b). It's part of the boot process.

Error auto-detection (our addition). pskoett's system captures lessons that a human (or agent) explicitly writes. Our system auto-logs every non-zero exec exit to ERRORS.md immediately, without waiting for anyone to decide it's worth recording.

Scaled-down format (our choice). pskoett's system uses full JSON rule files with complex schemas. We stripped that to plain markdown tables in .learnings/ files. Less powerful but dramatically simpler to maintain—anyone can edit a markdown table with vim.

What We Skipped

Skill extraction. pskoett's system includes automatic skill extraction from session transcripts. This is elegant but computationally expensive and prone to false positives. We decided human-in-the-loop pattern recognition was more reliable for our scale.

Hook scripts. pskoett uses filesystem hooks to trigger learning actions on file changes. We replaced this with behavioural prompts in AGENTS.md—the agent is instructed to log errors and lessons as part of its standard operating procedure. Less reactive but more predictable.

Our system isn't strictly "better." pskoett's is more ambitious in scope and more autonomous. Ours is more pragmatic, more human-auditable, and better suited to a setup where the human wants visibility into what the agent is learning.

10. Real-World Motivation

This architecture wasn't designed in a vacuum. It was forged from real incidents—each one a pattern that a stateless agent would repeat indefinitely without a learning system.

Pattern 1: The Timezone Bug

A backup health check compared file modification timestamps against calendar days. It worked perfectly—except when a backup ran just after midnight UTC, producing a timestamp in the "wrong" day. The check flagged a healthy backup as failed. After the third occurrence in a month, the lesson was codified: "Always use UTC-aware datetime comparisons in backup health checks."

Pattern 2: nginx Location Collisions

An agent created a static HTML page at a path like /login.html. The nginx configuration had a regex location block that proxied /login to a backend application. The static file was never served. This happened three times across different projects before the rule was codified: "Before creating any static page, grep nginx config for location conflicts."

Pattern 3: Postfix Pipe Script Permissions

A Python script used as a Postfix pipe transport was deployed with chmod 644 (readable but not executable). Postfix's pipe transport executes scripts directly—without the execute bit, mail silently deferred. The rule: "Pipe scripts get 755, not 644. Always verify by checking the transport type."

Pattern 4: Sender Verification Surprises

An email forwarding system used the original sender's address as the From header when relaying through an email API. The API rejected the message because the sender's domain wasn't verified in the account. The rule: "Never pass through an unverified From address. Put original sender info in the body, not the Reply-To header."

Each of these patterns followed the same trajectory: mistake → fix → session ends → next session starts → same mistake. With T-Learning, the rule loads at session startup and the agent reads it before touching the relevant subsystem.

11. Setup Guide

11.1 Prerequisites

  • OpenClaw (or any agent framework that supports pre-session and post-session hooks)
  • SSH key-based access between your gatekeeper machine and worker machines
  • Python 3.9+ (stdlib only—no pip dependencies)
  • A filesystem accessible to both the agent and your hook scripts

11.2 Directory Structure

On each worker agent:

mkdir -p /opt/openclaw/workspace/rules/alerts/pending
mkdir -p /opt/openclaw/workspace/scripts
git init /opt/openclaw/workspace/rules

On your gatekeeper (Mac mini/Conductor):

mkdir -p ~/.openclaw/workspace/tasks
mkdir -p ~/.openclaw/workspace/.learnings
mkdir -p ~/.openclaw/workspace/scripts

11.3 Seed Critical Rules

Create /opt/openclaw/workspace/rules/critical.jsonl:

{"id":"CONDUCTOR-001","version":1,"rule":"Always verify file permissions after deploying to VPS","rationale":"gunicorn runs as www-data; files deployed as vincent:vincent cause PermissionError","category":"deploy","scope":["general"],"source":"conductor","priority":"critical","maturity":"active","created":"2026-05-23T00:00:00Z","last_triggered":null,"trigger_count":0,"expires":"2026-08-21T00:00:00Z","refs":[],"contradicts":null}

11.4 Create the Narrative Learning File

Create ~/.openclaw/workspace/tasks/lessons.md:

## LESSON-20260523-001 — Always verify file permissions after deploying

**Date:** 2026-05-23 | **Project:** general | **Category:** deploy | **Learnings-Ref:** LRN-20260523-001

**Mistake:** Deployed a Flask app to the VPS under vincent:vincent with 644 permissions. gunicorn runs as www-data and couldn't read the files.

**Root Cause:** Assumed the deploy user and the runtime user were the same.

**Resolution:** Changed deploy script to chown www-data:www-data and chmod 755 for directories, 644 for files.

**Rule:** Always verify file permissions after deploying to VPS.

11.5 Create the Structured Learning File

Create ~/.openclaw/workspace/.learnings/LEARNINGS.md:

# Structured Learnings
| ID | Rule | Category | Status | Scope | Recurrence-Count | First-Seen | Last-Seen | Action | Lessons-Ref |
|---|---|---|---|---|---|---|---|---|---|
| LRN-20260523-001 | Always verify file permissions after deploying | deploy | resolved | general | 3 | 2026-05-01 | 2026-05-23 | Automate | LESSON-20260523-001 |

11.6 Install the Scripts

Copy all three scripts to /opt/openclaw/workspace/scripts/ and make them executable:

chmod 755 /opt/openclaw/workspace/scripts/load_rules.py
chmod 755 /opt/openclaw/workspace/scripts/write_rule.py
chmod 755 /opt/openclaw/workspace/scripts/rules_alert.py

11.7 Wire Up Agent Startup

Add to your agent's AGENTS.md as step 3b:

3b. **Check .learnings/ items:** Run review-weekly.sh for high-priority items,
    recurrence warnings, and active promotions

# Before session prompt assembly:
python3 /opt/openclaw/workspace/scripts/load_rules.py general,wescan
# Inject output: "The following rules from past sessions apply: ..."

11.8 Wire Up Post-Session Reflection

export WRKR_SESSION_START="2026-05-23T03:00:00Z"
echo '{"rule":"Always check DNS before assuming DKIM works","category":"sendgrid","scope":["wescan"],"priority":"high","source":"worker"}' \
  | python3 /opt/openclaw/workspace/scripts/write_rule.py

11.9 Set Up the Review Cadence

Install the review scripts and configure OpenClaw cron:

# OpenClaw cron config (config.json):
{
  "cron": {
    "review-weekly": "0 9 * * 1",
    "review-monthly": "0 9 1 * *"
  }
}

11.10 Connect the Alert Queue to Email

Add a cron job on your gatekeeper:

0 9 * * * /usr/local/bin/pull_and_alert.sh

The pull_and_alert.sh script:

#!/bin/bash
REMOTE="user@worker-host:/opt/openclaw/workspace/rules/alerts/pending/"
LOCAL="/tmp/rules-alerts/"
rsync -az "$REMOTE" "$LOCAL" --include='*.json' --exclude='*'
for alert in "$LOCAL"*.json; do
  [ -f "$alert" ] || continue
  python3 /opt/openclaw/scripts/send_email.py \
    --to you@example.com \
    --subject "[T-Learning Alert] $(jq -r .type "$alert")" \
    --body "$(jq -r .message "$alert")"
  ssh user@worker-host "mv /opt/openclaw/workspace/rules/alerts/pending/$(basename $alert) /opt/openclaw/workspace/rules/alerts/sent/"
done

12. Lessons Learned

What Worked

JSONL was the right call. Being able to grep the rule files, wc -l for counts, and tail -1 for the latest addition made debugging trivial. No database queries, no connection pool config, no ORM migrations.

The two-layer design solved the "why" problem. Before we added the narrative layer, reviewing the rule base was confusing. Now the structured layer tells the agent what to do, and the narrative layer tells the human why. Both are cross-referenced.

Auto-error-detection caught things we'd have missed. In the first week, ERRORS.md captured three patterns that wouldn't have been logged otherwise: a flaky SSH connection that succeeded on retry, a transient Postfix config warning, and a pip install that fell back to a slower mirror.

The review cadence kept the system healthy. Before automation, the learning files accumulated stale entries. The weekly review catches these before they become noise.

What We'd Do Differently

Contradiction detection is currently explicit-only. Two rules only conflict if one explicitly lists the other in its contradicts field. Semantic contradiction detection would be valuable but is computationally expensive.

The 90-day expiry might be too aggressive for some domains. Infrastructure rules change slowly. Per-category expiry windows would be more sophisticated, but we valued simplicity over precision.

Scope matching is binary. A rule scoped to ["wescan"] doesn't load for ["realform"]. A cross-pollination mechanism would be valuable. On the roadmap.

We should have added auto-error-detection earlier. This was an afterthought in v5 and immediately became one of the most valuable parts. Add it from day one.

What to Watch Out For

  • Bankruptcy false positives. During onboarding, an agent might legitimately write 15+ rules in one session. Conductor reviews and clears the flag.
  • SSH key rotation. Remember to update the command= restriction on the worker's authorized_keys.
  • The WRKR_SESSION_START env var. If your agent framework doesn't set it, bankruptcy detection won't fire.
  • Git auto-commit frequency. Auto-committing after every rule write can produce noise. Consider batching.
  • Recurrence count inflation. A recurrence must be across 2+ distinct tasks within 30 days. A pattern that recurs within the same session doesn't count.

T-Learning is under 250 lines of Python, has zero dependencies, and adds no infrastructure. It's the simplest possible system that solves a genuinely hard problem: giving AI agents a persistent, self-tuning, self-expiring memory across sessions and across machines.

If your agents keep making the same mistakes, the fix isn't a better model. It's recursive learning—the ability to capture, remember, and apply lessons across every session. On OpenClaw, it's three files, an SSH key, and a self-improvement loop away.
