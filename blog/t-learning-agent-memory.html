A practical system for capturing lessons, avoiding repeat mistakes, and building AI agents that improve over time.

1. The Problem: Why AI Agents Need Memory

AI agents are fundamentally stateless. Every session starts from a clean slate. The context window is a blank page—and it stays that way because the architecture gives no affordance for persistence between invocations.

This creates four problems that compound over time:

Same mistakes, every time. An agent discovers that a particular nginx configuration breaks certain static pages. It documents this, fixes the issue, and moves on. Next session? The lesson is gone. The same four-hour debugging loop repeats.

Context windows are limited. Even with 200K+ token windows, you can't pack every past lesson into every prompt. The economics of token usage degrade as you shove more history into each call. You need selectivity—load only what's relevant to this task.

Knowledge silos between agents. In our setup, Conductor (a reviewer/gatekeeper/architect on a Mac mini) and Worker (a coding agent on a remote VPS) each learn different lessons from different contexts. Without a shared mechanism, Worker's hard-won deploy lessons never reach Conductor. Conductor's architectural directives never constrain Worker.

No forced forgetting. A human developer naturally forgets obsolete patterns. An AI agent with infinite memory accumulates rules forever—including rules that are no longer relevant, rules that contradict newer ones, and rules from codebases that have been rewritten. Without expiry, the rule base becomes noise.

T-Learning v2 is our answer to all four problems. It's a tiered, self-expiring, contradiction-aware rule system that runs on zero additional infrastructure—just JSONL files, SSH, and three Python scripts.

2. Design Principles

We made deliberate architectural choices. Here's each one, with its rationale.

File-Based Over Database

A PostgreSQL-backed rule store would be elegant. It would also be another service to monitor, another connection string to manage, and another failure mode. Our agents already have working filesystems. JSONL files are trivially inspectable with cat and grep, infinitely portable, and require zero setup. For a rule base of hundreds (not millions) of entries, the filesystem is the perfect database.

SSH-Mediated Over GitHub

Worker has no direct access to the Mac mini. All cross-agent communication flows one direction: Mac mini → Worker via SSH push. This is intentional—the Mac mini is the gatekeeper, and Worker is the worker. Conductor pushes critical rules to Worker, and pulls Worker's learned rules back for review. No shared infrastructure, no central server, no authentication tokens to leak. Just SSH keys with restricted command= directives.

JSONL Over YAML

YAML is readable but dangerous: anchors, aliases, and the Norway problem (no → false) make it a poor serialisation format for machine-written data. JSONL (one JSON object per line) is concurrent-append-safe—multiple writers can append lines without corrupting each other's data. There's no parser ambiguity, no RCE vector (Python's yaml.load), and no split-brain risk. Each line is self-validating.

Tiered Knowledge

Not all rules are equal. Some are always relevant (critical rules: "never deploy without verifying permissions"). Some are project-specific (WeScan deployment rules shouldn't load for a Realform session). Some are niche and rarely needed (a one-off SendGrid API quirk). We use three tiers:

TierFileWhen Loaded
Criticalcritical.jsonlAlways, for matching scope
Directivesdirectives.jsonlAlways, filterable by scope
Learnedlearned.jsonlFiltered by scope, capped at 50

Forced Forgetting

Every rule has a 90-day expiry. A rule that never triggers in 90 days almost certainly isn't useful. Rules that do trigger get auto-renewed—the system rewards relevance. Stale rules (60+ days since last triggered) are downgraded and eventually archived. This prevents rule bloat without any human intervention.

Degradation-First Philosophy

The system must never block actual work. If a JSONL file is missing, corrupt, or unreadable—continue with zero rules. If SSH to the remote agent fails—continue with local rules only. If a line can't be parsed as JSON—skip it and log a warning. The agent always proceeds. Rules are an enhancement, not a prerequisite.

Bankruptcy Protection

A buggy session could theoretically flood the rule base with hundreds of low-quality entries. We cap at 10 new rules per session. Exceed that, and the system enters lockdown—all new rules are rejected, and an alert fires. This isn't just about storage; it's about maintaining signal-to-noise ratio in the rule base.

Contradiction Kill Switch

What happens when one rule says "always do X" and another says "never do X"? Both get archived. Immediately. The contradiction is flagged for human review. The system refuses to pick sides—that's for a human to resolve.

Repeat Mistake Escalation

If Conductor detects the same mistake pattern more than three times within 30 days—despite existing rules meant to prevent it—the system escalates. New rule writing is deferred. An email goes to the human: "Worker keeps hitting X pattern despite rule Y. Review needed." This is the ultimate circuit breaker.

Data flow is unidirectional for writes. Conductor pushes rules to Worker. Worker writes locally and Conductor pulls. Worker never initiates connections to the Mac mini. This simplifies firewall rules and reduces the attack surface.

Two Agents, Two Roles

Conductor (Mac mini) is the reviewer and gatekeeper. It reads Worker's learned rules during daily health checks, promotes valuable rules to critical, detects contradiction patterns, and sends email alerts. It also writes directives (directives.jsonl) that encode architectural decisions—like "always check nginx location blocks before creating static pages."

Worker (VPS) is the coding agent. At session startup, it loads all three rule files, filters by the project context, detects contradictions, and enforces the 50-rule cap. During the session, it consults loaded rules before making decisions. At session end, it reflects on what was learned and writes new rules via write_rule.py.

4. The Rule Format

Every rule is a single JSON object on one line. No trailing commas. No multi-line values. Fully self-describing.

{
  "id": "WRKR-001",
  "version": 1,
  "rule": "Always check nginx location blocks before creating static pages",
  "rationale": "Creating /login.html when nginx proxies /login to Flask causes 404",
  "category": "infrastructure",
  "scope": ["wescan", "realform"],
  "source": "worker",
  "priority": "critical",
  "maturity": "active",
  "created": "2026-05-23T00:00:00Z",
  "last_triggered": null,
  "trigger_count": 0,
  "expires": "2026-08-21T00:00:00Z",
  "refs": ["WRKR-005"],
  "contradicts": null
}
FieldPurpose
idUnique identifier. WRKR-NNN for Worker-written rules, CONDUCTOR-NNN for Conductor directives.
versionStarts at 1, incremented on updates. Allows tracking rule evolution.
ruleThe actionable one-sentence rule. Max 200 characters. This is what the agent reads inline.
rationaleWhy this rule exists—the mistake it prevents. Max 500 characters. Invaluable for human review.
categoryClassification for filtering and reporting: infrastructure, security, deploy, code, nginx, etc.
scopeWhich projects this applies to: wescan, realform, strayaco, openclaw, general.
prioritycritical (always loaded), high, normal, low. Drives cap-enforcement ordering.
maturityLifecycle stage: captured → tested → active → stale → archived.
trigger_countHow many times this rule was consulted or relevant. Drives promotion.
expiresISO-8601, created + 90 days. Auto-renewed if trigger_count > 0.
contradictsArray of rule IDs this rule conflicts with. Mutual archive trigger.

5. Rule Lifecycle

captured ──→ tested ──→ active ──→ stale (60d) ──→ archived (90d) │ ↑ └──→ promoted ──→ critical.jsonl │ │ contradiction detected ──────────────┘ (mutual archive within same scope)
StageConditionAction
capturedNewly written, never triggeredDefault for new rules. Loaded at low priority.
testedTriggered at least onceAuto-promoted by loader. Rule has been useful.
activeTriggered 3+ times within expiry windowStable, proven rule. High confidence.
promotedTriggered 5+ timesMoved to critical.jsonl by Conductor review. Cross-project relevance confirmed.
stalelast_triggered > 60 days ago, not criticalWon't load automatically. Rule was situational.
archivedExpired, or stale > 90 days, or contradictedNot loaded. Kept for audit trail only.

Expiry is not deletion. Archived rules stay in the file—they're just excluded from session loading. This preserves the full audit trail. A human can always pull an archived rule back if it was a false positive.

6. Code Walkthrough

Three Python scripts form the engine. Together they're under 250 lines. Here's each one, annotated.

6.1 load_rules.py — Session Startup Loader

Runs at the start of every Worker session. Must be fast (<500ms). Reads all three rule files, filters by scope, detects contradictions, enforces the 50-rule cap, and outputs the loaded rule set.

#!/usr/bin/env python3
"""T-Learning: Rule loader for Worker."""
import json
import os
import sys
from datetime import datetime, timezone, timedelta
RULES_DIR = "/opt/openclaw/workspace/rules"
MAX_RULES = 50
PRIORITY_ORDER = {"critical": 0, "high": 1, "normal": 2, "low": 3}
def load_jsonl(path: str) -> list:
    """Load a JSONL file, skipping corrupt lines."""
    rules = []
    if not os.path.exists(path):
        print(f"[Rules] File not found: {path}")
        return rules
    with open(path) as f:
        for i, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                rule = json.loads(line)
                rules.append(rule)
            except json.JSONDecodeError:
                print(f"[Rules] WARNING: Corrupt line {i} in {path}, skipping")
    return rules
def has_contradiction(a: dict, b: dict) -> bool:
    """Check if two rules explicitly contradict."""
    if a.get("contradicts") and b["id"] in a["contradicts"]:
        return True
    if b.get("contradicts") and a["id"] in b["contradicts"]:
        return True
    return False
def check_age(rule: dict) -> dict:
    """Update maturity based on expiry and last_triggered."""
    now = datetime.now(timezone.utc)
    try:
        expires = datetime.fromisoformat(rule["expires"])
        if now > expires:
            if rule.get("trigger_count", 0) == 0:
                rule["maturity"] = "archived"
            else:
                rule["expires"] = (now + timedelta(days=90)).isoformat()
                rule["maturity"] = "active"
    except (ValueError, KeyError):
        pass
    if rule["maturity"] == "active" and rule.get("last_triggered"):
        try:
            last = datetime.fromisoformat(rule["last_triggered"])
            days_since = (now - last).days
            if days_since > 60:
                rule["maturity"] = "stale"
            if days_since > 90:
                rule["maturity"] = "archived"
        except (ValueError, KeyError):
            pass
    return rule
def load_rules(session_scopes: list) -> list:
    """Main entry point. Returns filtered, sorted, capped rules."""
    all_rules = load_jsonl(os.path.join(RULES_DIR, "critical.jsonl")) \
              + load_jsonl(os.path.join(RULES_DIR, "directives.jsonl")) \
              + load_jsonl(os.path.join(RULES_DIR, "learned.jsonl"))
    # Age checks + scope filter + contradiction detection
    all_rules = [check_age(r) for r in all_rules]
    scoped = [r for r in all_rules
              if set(r.get("scope", ["general"])) & set(session_scopes)]
    active = []
    for r in scoped:
        if r["maturity"] in ("archived", "stale"):
            continue
        for a in active:
            if has_contradiction(a, r):
                a["maturity"] = "archived"
                r["maturity"] = "archived"
                write_alert("contradiction", f"Contradiction: {a['id']} vs {r['id']}")
                break
        else:
            active.append(r)
    # Sort by priority → trigger_count desc → newest
    active.sort(key=lambda r: (
        PRIORITY_ORDER.get(r.get("priority", "normal"), 99),
        -r.get("trigger_count", 0),
        r.get("created", "")
    ))
    if len(active) > MAX_RULES:
        active = active[:MAX_RULES]
    return active

Key details:

  • load_jsonl() skips corrupt lines—a partially-written line from a crash won't block startup.
  • check_age() auto-renews rules that have triggered at least once. Rules that never triggered are archived.
  • Contradiction detection uses the contradicts field. If rule A lists rule B as a contradiction, both are archived.
  • The sort key prioritises critical rules, then high-trigger-count rules, then newest—so the 50-rule cap keeps the most valuable ones.

6.2 write_rule.py — Post-Session Writer

Called at the end of a session when Worker identifies a new lesson. Validates, deduplicates, checks for contradictions, enforces bankruptcy limits, and performs an atomic append.

#!/usr/bin/env python3
"""T-Learning: Rule writer for Worker."""
import json, os, sys
from datetime import datetime, timezone, timedelta
from difflib import SequenceMatcher
RULES_DIR = "/opt/openclaw/workspace/rules"
VALID_CATEGORIES = {"infrastructure", "security", "deploy", "pipelines",
                       "code", "process", "postgres", "python",
                       "nginx", "postfix", "sendgrid", "config"}
BANKRUPTCY_LIMIT = 10
def similarity(a: str, b: str) -> float:
    return SequenceMatcher(None, a.lower(), b.lower()).ratio()
def get_next_id(rules: list, prefix: str = "WRKR") -> str:
    max_num = 0
    for r in rules:
        rid = r.get("id", "")
        if rid.startswith(prefix):
            try:
                max_num = max(max_num, int(rid.split("-")[1]))
            except (IndexError, ValueError):
                pass
    return f"{prefix}-{max_num + 1:03d}"
def check_bankruptcy() -> bool:
    learned = load_jsonl(os.path.join(RULES_DIR, "learned.jsonl"))
    session_start = os.environ.get("WRKR_SESSION_START")
    if not session_start:
        return False
    try:
        start = datetime.fromisoformat(session_start)
        recent = [r for r in learned
                  if datetime.fromisoformat(r.get("created", "1970")) > start]
        return len(recent) >= BANKRUPTCY_LIMIT
    except (ValueError, KeyError):
        return False
def write_rule(rule_data: dict) -> dict:
    if check_bankruptcy():
        return {"id": None, "status": "bankrupted"}
    # Validate required fields
    for field in ["rule", "category", "scope", "priority", "source"]:
        if field not in rule_data:
            return {"id": None, "status": "invalid", "message": f"Missing: {field}"}
    # Load all rules for dedup and contradiction check
    all_rules = load_jsonl(os.path.join(RULES_DIR, "learned.jsonl")) \
              + load_jsonl(os.path.join(RULES_DIR, "directives.jsonl")) \
              + load_jsonl(os.path.join(RULES_DIR, "critical.jsonl"))
    # Duplicate check: 80%+ text similarity
    for r in all_rules:
        if similarity(r["rule"], rule_data["rule"]) > 0.8:
            return {"id": r["id"], "status": "duplicate"}
    # Fill metadata
    now = datetime.now(timezone.utc)
    rule_data.setdefault("version", 1)
    rule_data.setdefault("maturity", "captured")
    rule_data.setdefault("trigger_count", 0)
    rule_data.setdefault("refs", [])
    rule_data["id"] = get_next_id(all_rules, "WRKR")
    rule_data["created"] = now.isoformat()
    rule_data["expires"] = (now + timedelta(days=90)).isoformat()
    # Atomic append: write to temp, concat old content, rename
    new_line = json.dumps(rule_data, sort_keys=True) + "\n"
    temp = os.path.join(RULES_DIR, "learned.jsonl.tmp")
    real = os.path.join(RULES_DIR, "learned.jsonl")
    with open(temp, "w") as f:
        f.write(new_line)
    if os.path.exists(real):
        with open(real) as old, open(temp, "a") as new:
            new.write(old.read())
    os.rename(temp, real)
    return {"id": rule_data["id"], "status": "written"}

Key details:

  • Atomic append: Write new line to a .tmp file, concatenate existing content, then os.rename(). POSIX guarantees rename is atomic—readers see either the old file or the new file, never a half-written one.
  • Dedup uses SequenceMatcher: 80% text similarity threshold. Prevents near-identical rules from piling up.
  • Bankruptcy check uses WRKR_SESSION_START environment variable. Worker's session runner sets this before calling the writer.
  • Auto-incrementing IDs scan all three files for the highest existing number. No central counter to maintain.

6.3 rules_alert.py — Alert Queue Writer

Standalone script for writing alert files. Called by both load_rules.py and write_rule.py when they detect issues.

#!/usr/bin/env python3
"""T-Learning: Alert queue writer."""
import json, os, sys
from datetime import datetime, timezone
ALERT_DIR = "/opt/openclaw/workspace/rules/alerts/pending"
def write_alert(alert_type: str, message: str, severity: str = "P1"):
    os.makedirs(ALERT_DIR, exist_ok=True)
    alert = {
        "type": alert_type,
        "message": message,
        "severity": severity,
        "timestamp": datetime.now(timezone.utc).isoformat()
    }
    path = os.path.join(ALERT_DIR, f"{alert_type}-{int(datetime.now().timestamp())}.json")
    with open(path, "w") as f:
        json.dump(alert, f)
if __name__ == "__main__":
    if len(sys.argv) < 3:
        print("Usage: rules_alert.py <type> <message> [severity]")
        sys.exit(1)
    write_alert(sys.argv[1], sys.argv[2], sys.argv[3] if len(sys.argv) > 3 else "P1")

Key details:

  • Alerts are individual JSON files in alerts/pending/. Conductor's daily cron scans this directory, sends alerts via email, and moves files to alerts/sent/.
  • No network calls. No SendGrid API key on Worker. The worker writes files; the gatekeeper handles delivery.
  • Unix timestamps in filenames prevent collision even under high-frequency alerting.

Alert priority levels: P0 (rule bankruptcy, critical rule violation) demands immediate attention. P1 (contradiction detected, file corruption) should be reviewed within 24 hours. P2 (monthly digest) is informational.

7. Fail-Safes & Loop Prevention

Self-modifying systems are dangerous. Without safeguards, they loop, bloat, or oscillate. We built five independent mechanisms that interlock.

7.1 Forced Forgetting (Expiry)

Every rule expires 90 days after creation. Rules that have triggered at least once get auto-renewed for another 90 days. Rules that never triggered are archived. Rules that went 60+ days without triggering are marked stale and eventually archived. This is self-tuning—useful rules stay, noise fades.

7.2 Bankruptcy Protection

If Worker writes more than 10 rules in a single session, the system enters lockdown. All subsequent writes are rejected. An alert fires. This prevents a single buggy session (a hallucinating model, a misconfigured pipeline) from polluting the entire rule base.

Recovery from bankruptcy: Conductor reviews the rejected rules and decides which (if any) to manually promote. The bankruptcy flag is session-scoped—it clears automatically on next session start.

7.3 Contradiction Kill Switch

When load_rules.py detects two rules with overlapping scope that explicitly reference each other in their contradicts fields, both are archived immediately. Neither is loaded. An alert goes to the human. The system does not attempt to resolve the contradiction—it defers to human judgment.

7.4 Repeat Mistake Escalation

Conductor's daily health check scans session logs. If it detects the same mistake pattern more than three times in 30 days—despite active rules meant to prevent it—the system escalates. New rule writing is deferred. Conductor emails the human with a specific recommendation: "Worker keeps hitting X pattern. Rule Y should prevent it but isn't working. Review the rule, the process, or the enforcement."

7.5 Degradation (Never Blocking)

This is the most important fail-safe. Under no circumstance does the rule system prevent productive work:

FailureBehaviour
Rule file missingContinue with 0 rules
SSH to remote agent failsContinue with local rules only
Corrupt JSON line in fileSkip line, log warning, continue
All three files missingContinue with empty ruleset
Write failure (disk full)Log error, continue session without writing
Bankruptcy triggeredReject new writes, continue session with loaded rules

The agent always proceeds. Rules are an enhancement layer, not a dependency.

8. Real-World Motivation

This architecture wasn't designed in a vacuum. It was forged from real incidents—each one a pattern that a stateless agent would repeat indefinitely without a learning system. Here are the patterns that drove this work (anonymised, but structurally accurate):

Pattern 1: The Timezone Bug

A backup health check compared file modification timestamps against calendar days. It worked perfectly—except when a backup ran just after midnight UTC, producing a timestamp in the "wrong" day. The check flagged a healthy backup as failed. The agent fixed the symptom (re-running the backup) but never learned to use timezone-aware comparisons. After the third occurrence in a month, the lesson was codified: "Always use UTC-aware datetime comparisons in backup health checks."

Pattern 2: nginx Location Collisions

An agent created a static HTML page at a path like /login.html. The nginx configuration had a regex location block that proxied /login (and anything matching the prefix) to a backend application. The static file was never served—nginx intercepted the request and sent it to the app, which returned 404. This happened three times across different projects before the rule was codified: "Before creating any static page, grep nginx config for location conflicts."

Pattern 3: Postfix Pipe Script Permissions

A Python script used as a Postfix pipe transport was deployed with chmod 644 (readable but not executable). Postfix's pipe transport executes scripts directly—without the execute bit, mail silently deferred and eventually bounced. The agent had deployed dozens of Flask files with 644 successfully (gunicorn imports them, doesn't execute them) and applied the same pattern to a pipe script. The rule: "Pipe scripts get 755, not 644. Always verify by checking the transport type."

Pattern 4: Sender Verification Surprises

An email forwarding system used the original sender's address as the From header when relaying through an email API. The API rejected the message because the sender's domain wasn't verified in the account. The fix was to use a verified domain address as the sender and move the original address to Reply-To—but then that triggered phishing warnings in some email clients. The final solution (use the verified sender, include original sender info in the body) took three iterations to discover. The rule: "Never pass through an unverified From address. Put original sender info in the body, not the Reply-To header."

Each of these patterns followed the same trajectory: mistake → fix → session ends → next session starts → same mistake. The fix took four hours the first time and four hours the second time. With T-Learning, the rule loads at session startup and the agent reads it before touching the relevant subsystem.

9. Setup Guide

Ready to add recursive self-learning to your own agents? Here's the step-by-step.

9.1 Prerequisites

  • OpenClaw (or any agent framework that supports pre-session and post-session hooks)
  • SSH key-based access between your gatekeeper machine and worker machines
  • Python 3.9+ (stdlib only—no pip dependencies)
  • A filesystem accessible to both the agent and your hook scripts

9.2 Directory Structure

On each worker agent:

mkdir -p /opt/openclaw/workspace/rules/alerts/pending
mkdir -p /opt/openclaw/workspace/scripts
git init /opt/openclaw/workspace/rules

9.3 Seed Critical Rules

Create /opt/openclaw/workspace/rules/critical.jsonl with your first rule:

{"id":"CONDUCTOR-001","version":1,"rule":"Always verify file permissions after deploying to VPS","rationale":"gunicorn runs as www-data; files deployed as vincent:vincent cause PermissionError","category":"deploy","scope":["general"],"source":"conductor","priority":"critical","maturity":"active","created":"2026-05-23T00:00:00Z","last_triggered":null,"trigger_count":0,"expires":"2026-08-21T00:00:00Z","refs":[],"contradicts":null}

9.4 Install the Scripts

Copy all three scripts from the code walkthrough above to /opt/openclaw/workspace/scripts/. Make them executable:

chmod 755 /opt/openclaw/workspace/scripts/load_rules.py
chmod 755 /opt/openclaw/workspace/scripts/write_rule.py
chmod 755 /opt/openclaw/workspace/scripts/rules_alert.py

9.5 Wire Up Agent Startup

Add to your agent's startup hook (e.g., in OpenClaw's AGENTS.md or an equivalent pre-prompt injector):

# Before the session prompt is assembled:
python3 /opt/openclaw/workspace/scripts/load_rules.py general,wescan
# The output (loaded rules as JSON) is injected into the system prompt:
# "The following rules from past sessions apply to this project: ..."

9.6 Wire Up Post-Session Reflection

After each significant session, your agent should reflect and write rules:

# Set session start for bankruptcy tracking
export WRKR_SESSION_START="2026-05-23T03:00:00Z"
# Write a new rule
echo '{"rule":"Always check DNS before assuming DKIM works","category":"sendgrid","scope":["wescan"],"priority":"high","source":"worker"}' \
  | python3 /opt/openclaw/workspace/scripts/write_rule.py

9.7 Connect the Alert Queue to Email

On your gatekeeper machine, add a cron job to scan and deliver alerts:

# Daily at 9 AM: pull alerts, send via email, mark as sent
0 9 * * * /usr/local/bin/pull_and_alert.sh

The pull_and_alert.sh script:

#!/bin/bash
REMOTE="user@worker-host:/opt/openclaw/workspace/rules/alerts/pending/"
LOCAL="/tmp/rules-alerts/"
rsync -az "$REMOTE" "$LOCAL" --include='*.json' --exclude='*'
for alert in "$LOCAL"*.json; do
  [ -f "$alert" ] || continue
  python3 /opt/openclaw/scripts/send_email.py \
    --to you@example.com \
    --subject "[T-Learning Alert] $(jq -r .type "$alert")" \
    --body "$(jq -r .message "$alert")"
  ssh user@worker-host "mv /opt/openclaw/workspace/rules/alerts/pending/$(basename $alert) /opt/openclaw/workspace/rules/alerts/sent/"
done

10. Lessons Learned

After building and dogfooding T-Learning v2 across multiple projects, here's what we'd do differently and what to watch out for.

What Worked

JSONL was the right call. Being able to grep the rule files, wc -l for counts, and tail -1 for the latest addition made debugging trivial. No database queries, no connection pool config, no ORM migrations. The simplicity paid off every time we needed to inspect the system at 2 AM.

Degradation-first prevented outages. There were three instances where a corrupt rule file would have blocked agent startup if we'd made rules a hard dependency. Because they degrade gracefully, the agent always started and the corrupt file was fixed at leisure.

The alert queue pattern eliminated a security concern. Not putting SendGrid API keys on the worker VPS meant one less secret to manage, rotate, and audit. The file-based queue adds maybe 24 hours of latency to alerts—acceptable for a learning system.

What We'd Do Differently

Contradiction detection is currently explicit-only. Two rules only conflict if one explicitly lists the other in its contradicts field. We'd like to add semantic contradiction detection—where the loader infers a conflict from rule text analysis—but that's computationally expensive and prone to false positives. For now, explicit contradiction marking is a pragmatic trade-off.

The 90-day expiry might be too aggressive for some domains. Infrastructure rules change slowly. A rule about nginx behaviour is probably valid for years. A rule about a specific API quirk might be stale in weeks. Per-category expiry windows would be more sophisticated, but we valued simplicity over precision for v2.

Scope matching is binary. A rule scoped to ["wescan"] doesn't load for ["realform"], even if it's broadly applicable. A cross-pollination mechanism—"this WeScan rule was also useful in a Realform session"—would be valuable. That's on the roadmap for v3.

What to Watch Out For

  • Bankruptcy false positives. During initial onboarding, an agent might legitimately need to write 15+ rules in one session. We handle this by having Conductor review and manually clear the flag—but budget for this in your first week.
  • SSH key rotation. If you rotate the gatekeeper's SSH key, remember to update the command= restriction on the worker's authorized_keys. A misconfigured key silently breaks the sync.
  • The WRKR_SESSION_START env var. This is the single point of coupling between the session runner and the rule writer. If your agent framework doesn't set it, bankruptcy detection won't fire. Make it part of your session bootstrap.
  • Git auto-commit frequency. We auto-commit after every rule write. For high-frequency sessions, this can produce noise. Consider batching commits within a session.

T-Learning v2 is under 250 lines of Python, has zero dependencies, and adds no infrastructure. It's the simplest possible system that solves a genuinely hard problem: giving AI agents a persistent, self-tuning, self-expiring memory across sessions and across machines.

If your agents keep making the same mistakes, the fix isn't a better model. It's a better memory.
